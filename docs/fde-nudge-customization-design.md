# FDE 顧客別 nudge カスタマイズ設計

作成日: 2026-09-23

ステータス: 設計（未実装）

## 1. 決定

Cairn の FDE カスタマイズ面は、顧客別ダッシュボードではなく、**顧客の業務に合わせたプライベート nudge** とする。

FDE は顧客ごとに「何が起きたら、誰に、何を伝え、次に何をしてもらうか」を定義する。Cairn は共通のデータアクセス、権限、候補抽出、Jev 判定、配信、重複抑止、監査、コスト制御を提供する。顧客固有の条件を製品コードの分岐や顧客専用フォークへ埋め込まない。

利用者にダッシュボードを見に行かせず、普段いる会話の中へ必要なときだけ届ける。認証後の既定画面は `/chats` のままとし、旧 `PageDashboard` の復元や新しいダッシュボードの追加は本構想の対象外とする。

設定、シャドー評価、実行履歴、監査のための管理画面は将来ありうるが、それは配信面ではない。

## 2. プロダクト原則

1. **conversation first**
   利用者が別画面を巡回しなくても、該当チャンネルの会話内で気づけるようにする。
2. **沈黙を正常系にする**
   候補があっても、現在性、発話価値、行動可能な宛先のいずれかが欠ければ送らない。
3. **行動できる本人へ返す**
   管理者向けの監視ではなく、状況を変えられる本人だけに私的に届ける。
4. **顧客差分を宣言的な設定へ閉じ込める**
   任意 SQL、任意 JavaScript、任意 URL、顧客別 UI コンポーネントを許可しない。
5. **個別案件を共通基盤へ戻す**
   複数顧客で繰り返された検知器、評価基準、アクションは、業種別テンプレートまたは共通機能へ昇格させる。

## 3. FDE の成果物

FDE が新しい顧客へ提供する主成果物は、顧客専用画面ではなく**nudge レシピ**である。

| FDE が顧客ごとに定義するもの | Cairn の共通基盤が保証するもの |
|---|---|
| 業務上の見落とし、停滞、例外、好機 | ワークスペース境界とアクセス制御 |
| 候補を抽出する条件とデータ範囲 | 許可済みデータソースと検知器 |
| 対象となる役割、人物、チーム | active membership と宛先アクセスの再検証 |
| Jev に評価させる業務基準 | Jev 呼び出し、ZDR、利用量記録 |
| 文面、根拠、配置先チャンネル | 私的な nudge 表示と AI 表示 |
| 利用者が選べる次のアクション | 許可済みアクション、監査、失敗表示 |
| 配信を控える条件、頻度、時間帯 | 重複抑止、クールダウン、注意の予算、個人キルスイッチ |
| 共有が必要になる条件 | 本人の明示承認なしに公開しない境界 |

## 4. 処理の流れ

```text
heartbeat / イベント
        ↓
許可済み検知器による候補抽出
        ↓
顧客別 nudge レシピ
        ↓
Jev が現在性・発話価値・行動可能な宛先を判定
        ↓
権限・重複・頻度・静寂時間帯を再確認
        ↓
関係する本人の会話内へプライベート nudge
        ↓
対応する / あとで / 問題ない / 詳しく調べる
        ↓
必要なら本人の承認後にだけ共有チャンネルへ投稿
```

候補抽出は可能な限り決定論的に行う。Jev は大量の生データから自由生成するのではなく、候補の現在性、発話価値、宛先、根拠を評価するために使う。

定刻に必ず投稿する業務は nudge ではなく [`scheduled-jobs-design.md`](./scheduled-jobs-design.md) の cron が担当する。nudge の定期起動は評価の機会を作るだけであり、価値がなければ発言しない。

## 5. nudge レシピ

初期段階では、ワークスペース単位の宣言的な設定として保持する。以下は概念例であり、実装時の確定スキーマではない。

```ts
interface NudgeRecipe {
  id: string
  enabled: boolean
  trigger: 'heartbeat' | 'event'
  detector: string
  audience: string
  evaluator: string
  delivery: string
  messageTemplate: string
  actions: string[]
  cooldown: string
  priority: number
}
```

例:

```json
{
  "id": "project-leader-missing",
  "enabled": true,
  "trigger": "heartbeat",
  "detector": "project_role_missing",
  "audience": "workspace_admin_who_can_assign",
  "evaluator": "send_if_project_is_active_and_assignment_is_actionable",
  "delivery": "related_project_channel_private",
  "messageTemplate": "進行中の案件にリーダーが設定されていません。担当を決めますか？",
  "actions": ["open_project_members", "later", "not_helpful"],
  "cooldown": "7d",
  "priority": 100
}
```

`detector`、`audience`、`evaluator`、`delivery`、`actions` は自由記述コードではなく、Cairn 側の許可済みレジストリを参照する識別子とする。

Phase 3 のメッセージ埋め込みは nudge レシピの前提にしない。過去の議論がなければ成立しない具体的なレシピが見つかった場合にだけ、権限安全な履歴検索を追加する。

## 6. 配信とアクション

- nudge は原則として、根拠となったタスクやメッセージがあるチャンネルへ本人だけに表示する。
- チャンネルに置けない場合だけ通知ベルへ出し、専用ダッシュボードへ誘導しない。
- 根拠となる対象へ1操作で移動できるようにする。
- 共通アクションは「あとで」「これは問題ない」「詳しく調べる」とする。
- 業務操作は許可済みアクションに限定し、状態変更は本人の明示操作を経る。
- チーム共有が必要な場合も、自動エスカレーションせず「共有しますか？」と本人へ提案する。

## 7. FDE 導入手順

1. **業務発見**
   顧客が定例会、確認表、個別連絡で拾っている事象と、見落とした場合の損失を聞き取る。
2. **成果と行動の定義**
   「何を表示するか」ではなく「誰が何をすれば仕事が進むか」を一組で定義する。
3. **レシピ作成**
   既存の検知器、評価、配信、アクションを組み合わせ、不足する共通部品だけを追加する。
4. **シャドー評価**
   配信せずに候補、Jev の採否、宛先、根拠、費用を記録し、顧客と妥当性を確認する。
5. **限定公開**
   対象者と日次上限を絞って有効化し、nudge から実際に行動へ進んだかを測る。
6. **共通化判断**
   他顧客でも再利用できる部品はテンプレートまたは共通レジストリへ戻す。

成功指標は配信数や既読数ではなく、対象業務の見落とし減少、判断時間短縮、停滞解消、次の行動の完了率とする。

## 8. 安全境界

- すべての候補抽出は認証済みワークスペースと既存のアクセス制御を経由する。
- 配信時と読み取り時に、宛先の active membership と対象へのアクセスを再確認する。
- ゲストには参加プロジェクト外の候補、件数、存在を返さない。
- nudge の内容、存在、既読、反応を owner / admin を含む本人以外へ見せない。
- FDE 設定から任意 SQL、任意 URL、任意 JavaScript を実行しない。
- 管理者向けの個人ランキング、遅延者一覧、自動エスカレーションを作らない。
- AI が生成した説明だけを根拠にせず、元のプロジェクト、タスク、メッセージ等の ID を保持する。
- 個人キルスイッチ、重複抑止、クールダウン、静寂時間帯、日次上限を顧客設定より優先する。

## 9. 管理面の位置づけ

将来の管理画面が扱うのは、次に限定する。

- レシピの有効化、対象、文言、頻度、アクション
- シャドー評価の採否と費用
- 実行成否、エラー、レシピのバージョンと適用履歴
- 個人を特定しない集計による案件成果の検証

管理画面を認証後のホームにはしない。管理者が本人の nudge 本文や反応を閲覧する機能も作らない。

## 10. 段階導入

### Phase 1 — FDE 管理の宣言的レシピ

- 既存の AI PMO 基盤へ、許可済み検知器を組み合わせる顧客別レシピを追加する。
- 設定は FDE 向けの内部手段で投入し、顧客向けビルダーは作らない。
- シャドー評価後、1〜3レシピ、限定ユーザー、低い日次上限から始める。
- `/chats` を認証後の既定画面として維持する。

### Phase 2 — テンプレート化と外部連携

- 複数案件で再利用されたレシピを業種別テンプレートへ昇格する。
- 許可済みコネクタ、検知器、アクションを追加する。
- レシピのバージョン、公開、ロールバック、適用履歴を管理する。

### Phase 3 — 顧客管理者による限定編集

- FDE が繰り返し設定する項目だけを管理画面へ公開する。
- 自由なルールビルダーにはせず、テンプレート選択、文言、対象、頻度、ON/OFF に限定する。
- 私的な nudge の内容や反応は管理対象に含めない。

## 11. 実装開始条件

最初の顧客案件について、以下を確定してから実装する。

- 現在の定例会、確認表、レポート、個別連絡
- 最初に減らしたい見落としまたは停滞を1〜3件
- nudge を受ける本人と、その人が取れる具体的な行動
- 候補抽出に必要なデータと、そのデータへの本人のアクセス権
- 発話しない条件、許容頻度、適切なチャンネル
- 誤配信と見落としのどちらを重く扱うか
- シャドー評価期間と、顧客成果を測る指標

この情報がない段階では、汎用レシピビルダー、専用ダッシュボード、メッセージ全体の埋め込みを先に実装しない。
