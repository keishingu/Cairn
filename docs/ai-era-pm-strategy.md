# AI時代のプロジェクト推進ツール戦略 — 3つの逆転

作成日: 2026-07-17
ステータス: 記録（戦略議論の合意事項。実装設計は各リンク先が正）

従来のプロジェクト管理ツールは「**人間に記録させる装置**」だった——人がステータスを更新し、タスクを起票し、期限を入力することで、管理者向けのダッシュボードが成立する。その前提が AI 時代に3つの方向で逆転する、という認識と、それぞれに対する Cairn の座取りを合意した記録。

関連: [`ai-pmo-design.md`](./ai-pmo-design.md)（逆転②の実装設計）/ [`10_ai_member_design.md`](./10_ai_member_design.md) / [`09_product_strategy_notes.md`](./09_product_strategy_notes.md)

## 逆転① 記録 — 人が書く構造から、AIが聞き取る構造へ

タスク管理が形骸化する理由は常に同じで、「地図（かんばん・ステータス）の更新」が「現地（実際の仕事）」とは別の作業だから。人は仕事はするが記帳はしない。**AIに覚えさせるためにわざわざ記帳するのは本末転倒**であり、答えは入力UIの改善ではなく、構造（タスク・ステータス・決定事項）を**会話からの派生ビュー**にすることである。

- 情報の源泉は「会話」——チャット・議事録・音声・動画
- `tasks.sourceMessageId`（メッセージのチェックボックスからのタスク化）で既にこの方向に半歩踏み出している。次の一手は「人が明示的に変換する」から「AIが提案し人が承認する」への移行

### 会話ソースの取り込み方針（合意）

- **録音・文字起こし・要約のレイヤーは自前で作らない**。Circleback / Notta / Plaud 等の強豪がひしめき、一部はハードウェアも持つ領域であり、勝負しない
- webhook / API で議事録を受け取る**ネイティブ連携**に徹する。Cairn の陣地はその下流——外部で生成された会話データを**組織の文脈（プロジェクト・タスク・決定事項）に統合するレイヤー**

### 案件への紐付け（合意）

「この議事録はどの案件の会話か」を AI の事後推測に頼ると、誤紐付け事故が起きる。設計原則は以下。

1. **第一原則: 会議の後に推測するのではなく、会議の前に決定的に紐付ける**。会議はたいていカレンダー予定から生まれる。Cairn には `google_calendar_events` の同期が既にあり、カレンダー予定をプロジェクトに紐付けておけば（予定作成時に出席者∩プロジェクトメンバー・タイトルから AI が提案して確定）、後から届く議事録は予定を経由して**推測ゼロ**で正しい案件に落ちる
2. **AI 推測は「予定に紐付かない会話」のフォールバック**に格下げする
3. **フォールバックの承認者は管理者ではなく、その会議の出席者（またはアップロード者）**。どの案件の話かを最も知っているのは出席者であり、管理者は最も文脈がなく、ボトルネックにもなる
4. **未承認の議事録は誰にも公開しない（ペンディング状態）**。誤紐付け事故の本質は「間違ったプロジェクトのゲストに機密の議事録が見える」という**情報の越境**である。AI は確信度が高くても候補提示までとし、公開はしない。自動で公開してよい例外はカレンダー由来の決定的紐付けのみ（予定作成時に人間が既に判断しているため）

## 逆転② 視線 — マネージャーが見るダッシュボードから、本人に返すナッジへ

従来の PM ツールの隠れた顧客は管理者であり、だから現場に嫌われてきた。AI が全チャンネルを読める時代には「AI は監視装置になりうる」という恐怖が必ず生まれる。したがって**監視に構造的に使えないこと**が製品の競争力になる。

- 「このツールはチームの側に立つ。管理の側には立たない」——これは機能ではなく**憲法**。目指すのは「良い（優秀な）PMO」である以前に「**善いPMO**」であること: don't be evil
- 実装設計は [`ai-pmo-design.md`](./ai-pmo-design.md)（PMO常駐 + 本人だけに見えるプライベートナッジ）。同書 §2.3「やらないこと」が憲法の本文にあたる（公開の場での催促の禁止・管理者向け遅延一覧の拒否・自動エスカレーションの禁止）

## 逆転③ 実行 — 人に割り当てるタスクから、人とAIの混成チームへ

タスクの担当者欄に AI エージェントが並ぶのが当たり前になる。AI 担当分の進捗報告は自動化され、ボトルネックは常に人間側のタスクになる。PM ツールの仕事は「進捗の集計」から「人間の詰まりの解消」に移る。

### MCP サーバーとしての座取り（合意）

- スライド作成・経理等の**実行系 AI は自前で作らない**。実行ツールは無数に生まれる領域であり、勝負しない
- ChatGPT / Claude の Work API 開放を待つ必要もない。MCP のような標準により、**エージェント側が外部ツールに接続しに来る**方向に世界が動いている
- Cairn は「タスクの取得・成果物の投稿・完了報告」を **MCP サーバーとして公開**する。ユーザーが自分の Claude / ChatGPT エージェントを接続すれば、「資料、つくっておきました！」がプロジェクトチャンネルに届く
- つまり Cairn は実行を作らず、**エージェントが報告しに来る場所**（人と AI の混成チームの調整・記録レイヤー）になる
- 外部エージェントの身元管理は [`10_ai_member_design.md`](./10_ai_member_design.md) の agent 用 profile（`kind: 'agent'` 相当）を流用する

### 沈黙の設計（合意）

リモートワークの「誰も何も言わなくなる」現象への向き合い方。

- 対面で話が進む本当の理由は**ペースではなく宛先の特定**（目が合った人は答えざるを得ない）。チャットの沈黙は速度の問題ではなく**責任の拡散**（誰かが返すだろう、で誰も返さない）
- ただし沈黙は悪ではない。チャンネル参加は物理的制約を受けないため、全チャンネルを対面のペースで進めれば、人によっては永遠にタイピングし続けることになる。**非同期の良さ（熟考・注意の保護）は保つ**
- 解は「宙に浮いた問いにだけ、宛先を静かに復元する」——宛先復元ナッジ「この質問、あなたが一番答えられそうです（このメッセージはあなただけに見えています）」。設計は [`ai-pmo-design.md`](./ai-pmo-design.md) §5.2 の `unanswered_ask`
- ナッジの頻度上限が実質的な**注意の予算**として働く。目的は全員を速く返信させることではなく、進行を本当にブロックしている少数の「待ち」を、解消できる一人に、予算内で届けること
- 「結論が出ないまま議論が消える」ことだけは防ぐ。3日等の経過後に要約を**パブリックに再浮上**させる（「論点はAかBです」——誰も責めない形なので公開でも成立する）。[`ai-pmo-design.md`](./ai-pmo-design.md) Phase 4

## 3つの逆転を貫く複利資産 — 記憶

「なぜこの決定になったのか」「去年同じ問題でどう対処したか」に即答できる**組織記憶**は、使うほど溜まり、他ツールへの乗り換えを困難にする最大の資産になる。[`10_ai_member_design.md`](./10_ai_member_design.md) Stage 4 がこれを見据えている。毎年同じサイクルを回すが人が入れ替わる組織（大学の部活等）は、記憶の価値が最も高く出るドメインである。

一方で、**人間に残るべきものを奪わない**: 決めること・約束すること・責任を持つことはツールが代行しない。AI の役割は、記帳・催促・検索・集計という「プロジェクトの家事」を引き受け、人間がその3つに使える時間を最大化することである。
