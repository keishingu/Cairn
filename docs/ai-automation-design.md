## 1. 背景と想定ユースケース

山岳部での事故を受け、部内の審査を「経験ベース」で行う体制づくりが進んでいる。現状の課題は、振り返り資料がプロジェクトごとに散らばり、メンバーの経歴を一元的に把握できないこと。`/ai` へ毎回質問する方法では、質問した範囲しか答えないため網羅的に把握できず、全資料を手で入力することもできない。

求められていること:

1. **資料の収集**: 定期的に実行し、AI 自身が該当資料を見つける
2. **分析**: 振り返り資料に書かれた経験が、審査の各項目に当てはまるか判定する
3. **管理**: メンバーごとに一覧できる形でまとめる

具体的な指示の例:

| 種類 | 指示文の例 |
|---|---|
| cron | 毎日10時に #審議 チャットを確認し、計画を提出した人の経歴を過去のプロジェクトと添付ファイルから調べ、計画を遂行できる人物か判断して @審査担当 に報告する |
| heartbeat | このチャンネルの会話を確認し、プロジェクトが遅れそうな兆候を見つけたら、プロジェクトリーダーに非公開で知らせる |
| Skill（`$assign-reviewer`） | このプロジェクトに添付された計画書を読み、「コーチ」属性のユーザーのうち、過去に似た計画で「レビュワー」としてアサインされた人をプロジェクトに招待して「レビュワー」の役割を付ける。その後、招待した人に「レビュワーとしてアサインさせていただきました。ご確認お願いします！」とメンションする |

## 2. 決定事項

### 2.1 一つのモデルで表す

**オートメーション = 指示文 + 起動条件 + 読み取り範囲 + ツール + 結果の送り先**

| 起動条件 | いつ動くか | 発言 |
|---|---|---|
| **Skill** | 利用者が `$名前` で呼ぶ（`/ai`。後続で `/chat`） | 呼んだ場で結果を返す |
| **cron** | 定刻に**必ず**1回動く | 実行結果を必ず送る（何もなければ「該当なし」も可） |
| **heartbeat** | 1日4回（02:00 / 08:00 / 14:00 / 20:00 JST。AI PMO Phase 2 と同じ）起こされ、前回以降に新着がある場合だけ差分を見て AI が反応の要否を判断する | **沈黙がデフォルト**。要否の判定に AI PMO の発話ゲートを使う |

- **AI PMO のナッジは組み込みの cron（Phase 1 タスク巡回）と heartbeat（Phase 2 メッセージ巡回）である**。ユーザー定義の基盤を別に作ってから移すのではなく、**PMO の基盤（`ai_nudges`・差分カーソル・発話ゲート）を広げてユーザー定義を載せる**。PMO Phase 1/2 は組み込みオートメーション2件として登録する（§6・§8）。これは `scheduled-jobs-design.md` §1 の「AI PMO の cron をユーザー定義ジョブの基盤に流用しない」という方針を変更するもの
- 用語: **AI PMO** は組み込みオートメーションの総称、**ナッジ**（`ai_nudges`）は本人だけに見える非公開メッセージという**出力の形**、**cron / heartbeat / Skill** は**起動条件**を指す
- **発火の判定に LLM を使わない**。cron は `nextRunAt <= now` の比較で決め、heartbeat は差分カーソルに新着があるかで決める。LLM が動くのは発火後だけ

### 2.2 読み取り範囲と結果の送り先

| 起動条件 | 読み取り範囲 | 結果の送り先 |
|---|---|---|
| Skill（`/ai`） | 呼んだ本人の権限の範囲 | 呼んだ本人（`/ai` の会話内） |
| Skill（`/chat`・後続） | 呼んだ本人の権限の範囲 | 呼んだ本人にだけ見える表示で応答し、チャンネルへの投稿は承認後（§2.4）。どちらも §2.3 の根拠ルールを満たすものだけ |
| cron | 作成者本人の権限の範囲 | **非公開メッセージのみ**。宛先は根拠を閲覧できる人に限る（§2.3） |
| heartbeat | **紐づけたプロジェクトの中だけ**（プロジェクトチャンネル・タスク・ファイル） | そのプロジェクトのメンバーへの非公開メッセージ、またはそのプロジェクトチャンネル（承認カード経由。§2.4） |

- DM は、どの起動条件でも読まない（AI PMO §7 と同じ）
- 作成者が非活性になった、または admin でなくなった場合、そのオートメーションは停止する（`paused_reason` を残し、owner / admin に通知する）。誰の権限で読むかを曖昧にしない

### 2.3 根拠ルール — 送り先が見られない情報を混ぜない

結果に含める根拠（メッセージ・ファイル・タスク・プロジェクト・メンバーのプロフィール属性）は、ツールが返す evidence DTO（`10_ai_member_design.md` §2.3）としてサーバー側で追跡する。配信の直前に、**宛先の全員がすべての根拠に現在アクセスできるか**を `requireChannelAccess` / `requireProjectAccess` / `canAccessFile` 相当で検証する。

- 一部の宛先が見られない根拠がある場合は、その宛先への配信を**失敗**として記録し、作成者に知らせる。伏せ字にして送ることはしない（文面に要旨が残るため、伏せても漏れる）
- 本文の文字列から判定せず、ツールの戻り値で判定する。LLM が根拠を出さずに要旨だけ書くケースに備え、run の中で読んだ全 evidence を「読んだ根拠」として扱い、宛先の閲覧範囲を超えるものを1件でも読んでいれば、その宛先へは配信しない

### 2.4 書き込みは承認カードを通す

- 報告（非公開メッセージ・`/ai` への返答）だけは承認なしで実行する
- それ以外の書き込み（プロジェクト招待・役割付与・タスク作成・チャンネル投稿・メンション）は、AI が**実行案**を作り、承認カードで人間が承認・編集・却下する。承認した人を実行責任者として記録し、**承認者の権限で**実行する（承認者が実行できない操作は失敗させる）
- 承認者は、Skill では呼んだ本人、cron / heartbeat では作成者（または作成時に指定した admin 以上の人）
- 承認カードはアプリ基盤のカード型メッセージ（`app-platform-design.md` §4）で描く。`10_ai_member_design.md` の Stage 2 と同じ仕組みを使う
- 承認後の投稿・メンションの**送信者は AI の Bot profile**とし、メッセージに「○○さんが承認」を表示する。承認者の名義で投稿しない（AI が書いた文だと一目で分かるようにするため。`10_ai_member_design.md` §6-5）
- AI の Bot は**アプリ基盤の Bot と同じ仕組み**で作る。「Cairn AI」をファーストパーティのアプリとして各ワークスペースへ自動でインストールし、そのインストールの Bot profile（`app-platform-design.md` §3.2）で投稿する。認証・表示・無効化を別に作らない
- `/chat` から Skill を呼んだ場合、実行案と承認カードは**呼んだ本人にだけ**見せ（ナッジと同じく本人だけに見える表示）、承認後の投稿・メンションだけがチャンネルに出る。却下した案は誰にも見えない。実行案と承認・却下の記録は `ai_automation_runs` / `ai_pending_actions` に残る

### 2.5 作成できるのは admin 以上、一覧は公開

コストと誤った投稿の影響が大きいため、作成・編集・停止は owner / admin に限る。オートメーションの一覧（名前・指示文・起動条件・作成者・送り先・承認者）は **member 以上が閲覧できる**。§2.6 の許可条件を兼ねる。

### 2.6 AI PMO の禁止事項はユーザー定義には適用しない（公開を条件に許可）

`ai-pmo-design.md` §2.3 の「監視・査定・炙り出しの道具にしない」「リーダーへ自動エスカレーションしない」は、**組み込みの PMO にだけ**適用する。ユーザー定義のオートメーションで人物の評価やリーダーへの報告を行うことは、次を条件に許可する。

- admin が明示的に設定したものであること（§2.5）
- 指示文・送り先が member 以上の一覧で見られること（§2.5）。誰が何を誰に報告させているかを隠さない
- 人物の評価・報告を含む指示文には、保存時に「対象者の評価を報告する指示です。一覧でメンバーに公開されます」と注意を表示する
- 報告カードには、どのオートメーション（作成者名）からの報告かを表示する

組み込みの PMO が個人の側に立つ道具であることは変えない。ユーザー定義のものは組織が自分の責任で設定する道具として、透明性で釣り合いを取る。

### 2.7 プロフィール属性は、画面に見える範囲で AI も使う

`list_members` などのツールは、**実行主体（呼んだ本人 / 作成者）の画面に表示されるプロフィール属性**をそのまま返し、AI は属性で人を絞り込める（例: 「コーチ」属性のユーザー）。属性ごとの AI 利用許可フラグは設けない。画面で見えるものを AI 経由で見ても、新たな露出にはならないため。

- ツールが返した属性は、対象メンバーごとに evidence DTO として run に記録し、§2.3 の根拠ルールで配信前に検証する。宛先に表示されない属性を読んだ run は、その宛先へ配信しない
- 属性をメンバーの埋め込み（`member/upserted` のインデックス）へ入れることはしない（`profile-attributes-design.md` §7.3 のまま）。ツール呼び出しで都度読む

### 2.8 受信者はオートメーションごとに受信を止められる

- 受信者は、届いた報告カードから、そのオートメーションからの受信を止められる（`ai_automation_mutes`）。止めたら作成者に通知し、報告が届いていないことに作成者が気づけるようにする
- 組み込みの PMO は、従来どおり個人キルスイッチ（`profiles.ai_nudges_enabled`）で一括して止める。ユーザー定義のものは個人キルスイッチの対象外（業務上の報告を一括停止で取りこぼさないため。止めるなら個別に止めて作成者に伝わる形にする）

### 2.9 上限とテスト実行

- ワークスペースあたり、**ユーザー定義の**オートメーションは**定義20件**、**実行は1日100回**（JST の暦日で数える。Skill の呼び出し・cron・heartbeat の発火・dry-run の各 run を1回とし、`silent` も含む）まで。上限に達した実行は `skipped` として記録し、作成者に知らせる（同じオートメーションについて1日1回まで）。実際のクレジット消費を見て値を見直す
- 組み込みの PMO はこの定義数・実行回数に**数えない**。PMO の実行はスケジュールで決まり、ユーザー定義の実行枠を消費しない。PMO の量は従来どおり発話ゲートの日次上限（§6）で抑える
- **テスト実行（dry-run）**を設定画面に置く。実際にツールで読み、判断まで行い、結果を**設定画面にだけ**表示する（報告文・宛先・実行案・読んだ根拠・根拠ルールで届かない宛先）。配信・書き込み・承認カードの発行・ナッジの作成はしない。結果は実行履歴にも残す。クレジットは消費し、実行回数にも数える

### 2.10 メンバーの経歴一覧は既存画面 + `/ai` で賄う

- 一人ひとりの経歴（参加プロジェクト・期間・ステータス・プロジェクトの役割）は、既存のメンバー詳細（`/members/[id]`、`member-panel.tsx`）で見られる。新しい画面は作らない
- 全員を比較する表は、その都度 `/ai` で生成させる（Phase 0 の `list_members` / `get_member_history` を使う）。審査項目に当てはまるかの判定は cron の報告で行う
- 専用の比較表画面は、上記の運用で足りないことが分かってから検討する

## 3. 全体アーキテクチャ

```
[/settings/automations] 指示文 + 起動条件 + 範囲 + 送り先を入力 → 保存時コンパイル（§4）→ dry-run（§2.9）
   ▼
ai_automations（組み込みの PMO Phase 1/2 も行として持つ）
   │
   ├─ Skill:     /ai で `$名前` → 会話のストリーム内でエージェント実行
   ├─ cron:      Inngest cron（dispatcher, 5分ごと）→ nextRunAt <= now → automation/fire
   └─ heartbeat: Inngest cron（1日4回）→ 範囲内の差分カーソルに新着あり → automation/fire
   ▼
[Inngest fn: on-automation-fire]
   reserve run（冪等） → 実行
     組み込み: 既存の PMO 検知（ルール / Jev）
     ユーザー定義: エージェント実行（ツールは §5、上限は §10）
   → 報告の届け先は起動条件で分かれる（いずれも根拠ルール §2.3 を通す）
       組み込み PMO / cron:  発話ゲート → ai_nudges で宛先本人へ非公開配信
       heartbeat:           発話ゲート → ai_nudges でプロジェクトメンバーへ非公開配信
       Skill（/ai）:         呼んだ本人の /ai の会話へ応答
       Skill（/chat）:       呼んだ本人にだけ見える表示で応答（§2.4）
   → チャンネル投稿・メンション・招待・役割付与（heartbeat のプロジェクトチャンネル投稿、/chat Skill の結果投稿を含む）:
       承認カードを発行（ai_pending_actions）→ 承認後に Cairn AI の Bot が実行
   → run を success / failed / silent / skipped で確定
```

エージェントの実行は `/ai` の tool calling（Vercel AI SDK v4、`chatLanguageModel()` 経由）を共通化した関数で行い、`/ai`・cron・heartbeat で同じツール実装を使う。ツール側で、認証コンテキストではなく「実行主体（呼んだ本人 / 作成者）と読み取り範囲」を受け取って境界を引く。

## 4. 保存時コンパイル

指示文はそのまま実行時のプロンプトに使い（`rawInstruction` を正とする）、**構造化できる部分だけ保存時に確定する**。

| 確定するもの | 例 | 解決できない場合 |
|---|---|---|
| 起動条件・スケジュール | 毎日 10:00 JST | 保存エラー |
| 参照するチャンネル・プロジェクト | `#審議` → channelId | 名前の重複・不在は保存エラー |
| 宛先・メンション | `@審査担当` → userId | 同名が複数いれば保存エラー（発火時に名前で再解決しない） |
| Skill 名 | `assign-reviewer` | ワークスペース内で重複したら保存エラー |
| 書き込みの種類 | `invite_project_member`、`set_project_member_role`、`post_message` | 承認者が決まらなければ保存エラー |
| 人物評価・報告を含むか | 「遂行できる人物か判断して報告」 | 保存は止めず、§2.6 の注意を表示する |

指示文の中の人・グループ・チャンネルは、チャットと同じ呼び出し記号で書き、入力補完で ID に固定して保存する（2026-10-28 決定）。名前の推測で解決しないので、同名や改名で誤解釈しない。

| 書き方 | 保存形式 | 指すもの |
|---|---|---|
| `@鈴木` | `<@userId>` | メンバー |
| `@コーチ` | `<@attr:属性ID>` | そのプロフィール属性を持つメンバー（チャットで実装済み） |
| `@レビュワー` | `<@role:役割ID>` | そのプロジェクトの役割を持つメンバー。プロジェクトが決まる文脈（プロジェクトのチャンネル、プロジェクトを指定した指示文）でだけ候補に出す |
| `#審議` | `<#チャンネルID>`（指示文だけで使う） | チャンネル |

役割と属性も `@` にそろえる。呼ぶ側にとってはどちらも「その人たち」で、記号を使い分けさせる必要がないため。候補の一覧には種類（メンバー・属性・役割）を表示して区別する。`$` は Skill、`/` はスラッシュコマンドに使う。チャットでの `@役割` の通知展開は、Skill の呼び出しと同じ PR で入れる。

保存時に「次回 10/28 10:00 に #審議 を読み、@審査担当 に非公開で報告します。書き込みはしません」のように確定内容をプレビューする。

## 5. ツール

`/ai` の既存の読み取りツール（`list_projects` / `list_project_tasks` / `search_channel_messages` / `search_workspace_documents` / `get_project_risk_snapshot`）に、次を加える。**同じ実装を MCP にも公開する**（§7）。

### 5.1 読み取り（追加）

| ツール | 用途 |
|---|---|
| `list_channels` | 名前・種類・紐づくプロジェクトでチャンネルを探す |
| `read_channel_messages` | 期間・スレッドを指定して時系列で読む（`since` は cron の前回実行時刻、heartbeat の差分カーソル） |
| `get_project_members` | プロジェクトの参加者とプロジェクトの役割（`project_roles`） |
| `list_members` | メンバー一覧。画面に表示されるプロフィール属性を含み、属性で絞り込める（§2.7） |
| `get_member_history` | あるメンバーが参加したプロジェクト・役割・期間・添付された振り返り資料の一覧。メンバー詳細の参加プロジェクト一覧（`/api/workspaces/members/[userId]/projects`）と同じデータ |
| `read_file` | 添付ファイルの抽出済み本文（既存 `/api/files/[id]/content`） |

### 5.2 書き込み（承認カード経由）

| ツール | 承認 |
|---|---|
| `send_private_report` | 不要（§2.4）。根拠ルールは必須 |
| `invite_project_member` | 必要 |
| `set_project_member_role` | 必要 |
| `post_message`（メンションを含む） | 必要 |
| `create_task` | 必要 |

承認待ちは `ai_pending_actions`（`10_ai_member_design.md` §4.2）に置く。承認までに対象が変わった場合（プロジェクト削除、承認者の権限喪失）は、実行時に再検証して失敗させる。

## 6. データモデル（案）

```
ai_automations
  id, workspace_id → workspaces (cascade)
  kind            text   -- skill | cron | heartbeat
  builtin         text   -- null（ユーザー定義）| pmo_tasks | pmo_messages
  name            text   -- Skill は `$name` の name。ワークスペース内で一意
  raw_instruction text   -- 編集・表示・実行プロンプトの正（組み込みは null）
  compiled        jsonb  -- §4 で確定した schedule / channelIds / projectId / recipientIds / writeActions
  scope_project_id uuid → projects   -- ユーザー定義 heartbeat の読み取り範囲（必須）

  automation_id → ai_automations (set null)   -- 定義を削除しても記録は残す
```

- **差分カーソルは既存の `ai_scan_states` を広げる**。主キーを `channel_id` から `(automation_id, channel_id)` に変え、PMO Phase 2 の既存行は組み込みオートメーション `pmo_messages` の行へ移す。`next_unanswered_ask_*` は PMO 固有のまま残す
- **非公開メッセージの配信は `ai_nudges` を使う**（宛先本人だけに見え、チャット欄に合成表示され、ベル通知・Realtime の仕組みが揃っているため）。`automation_id` / `run_id` 列を足し、ユーザー定義からの報告は `detector = 'automation'` とする。一意制約 `(user_id, dedupe_key)` は変えず、ユーザー定義の `dedupe_key` は `automation:{automationId}:{関心事のキー}` と**オートメーションごとに名前空間を分ける**（関心事のキーは cron なら予定時刻、heartbeat なら根拠メッセージ ID など、同じ事象を指す限り同じ値にする）。異なるオートメーション同士、また PMO の既存キー（`task_due_soon:...` 等）とも衝突しない。カードには「このメッセージはあなただけに見えています」に加えて、どのオートメーション（作成者名）からの報告かと「このオートメーションの受信を止める」を表示する
- 発話ゲートのうち、重複抑止・静寂時間はユーザー定義にも適用する。**日次上限（1ユーザー1日3件）は組み込みの PMO だけ**に適用し、ユーザー定義の報告は §2.9 のワークスペース上限で抑える（業務上の報告が PMO の枠を食い合わないようにするため）

## 7. Cairn MCP の拡張

現在の MCP でチャンネルを読む手段は `search_messages`（部分一致・新しい順に最大50件）だけで、次のことができない。

- チャンネルの一覧取得（`#審議` を特定できない）
- 期間を指定した時系列の取得、スレッドの取得
- メンバー一覧・プロフィール属性の取得
- プロジェクトの参加者と役割の取得（`get_project` が参加者を返さない）

そのため、外部 AI で「メンバーの経歴一覧」を作ることができなかった。§5.1 の読み取りツールを MCP にも同じ実装で公開する（MCP 層は既存 Route Handler を呼ぶ薄い変換のまま。`mcp-server-design.md` §6）。これは Cairn 内のオートメーションを待たずに出せるので、最初に実装した（§8 Phase 0。MCP からは `/api/research/*` を呼ぶ。`mcp-server-design.md` §6）。

## 11. 未決事項

なし（2026-10-27 時点）。実装中に出た論点はここに追記する。

### 11.1 Phase 0 の実装で決めたこと（2026-10-28）

- MCP 用の Route Handler は `/api/research/*` にまとめ、`/ai` の tool と同じ関数（`workspace-research-directory.ts`）を呼ぶ。画面用の既存 API（`/api/workspaces/members` 等）は UI 向けの DTO で上限・evidence を持たないため、PAT / OAuth に開かない
- `get_member_history` は1回で最大50人を受け取る。tool calling が8ステップに制限されているため、1人ずつ呼ぶと全員の比較表を作れない
- `list_members` の属性絞り込みは「いずれかを持つ（OR）」。属性名は完全一致
- `read_channel_messages` は既定で30日前から古い順に読み、期間の上限は設けない（cron の `since` が前回実行時刻になるため）。続きは `(作成日時, ID)` のカーソルで読む
- プロジェクトのチャンネル名は画面と同じくプロジェクト名（マイルストーンはマイルストーン名）、スレッドはスレッド名で返す

### 11.2 Phase 1（承認カード + Bot 投稿）の実装で決めたこと（2026-10-28）

- 実行案は `ai_pending_actions` に置き、承認・却下できるのは `approver_id` の本人だけ（他人の案は 404 で存在も明かさない）。API（`/api/ai/pending-actions/[id]`・`/approve`・`/reject`）は人間のセッションだけで受け、PAT・MCP には開かない。外部の AI が承認を代行できると、人間の承認を挟む意味がなくなるため
- 期限は作成から7日。過ぎた案は `expired` にして承認させない。`pending → executing` を1つの UPDATE で取り、二重の承認や承認と却下の競合では片方だけを進める。実行に失敗した案は `failed` に理由を残して再実行しない（部分的に成功した操作を重ねないよう、AI に頼み直して新しい案にする）
- 承認時に編集できるのは、投稿の本文とタスクのタイトル・説明だけ。宛先・対象（チャンネル・プロジェクト・人・役割）は変えさせず、却下して頼み直してもらう
- 実行は承認者のリクエストの中で行う。プロジェクトへの追加・役割の変更・タスク作成は画面と同じ Route Handler を呼び、承認者の認可・検証・通知をそのまま通す
- 実行案を作る時点でも、承認者に見えない対象（チャンネル・プロジェクト・メンバー・役割）を指す案は作らず、AI に誤りとして返す
- 投稿は「Cairn AI」（ファーストパーティのアプリ、slug `ai`）の Bot が行い、本文の下に「○○さんが承認」を添える。メンション通知は本文のメンションから通常どおり届く。実行案の ID を投稿 ID（`client_msg_id`）にして二重投稿を防ぐ
- Cairn AI がまだ参加していないチャンネルへの投稿を承認すると、承認者の操作として Bot をそのチャンネルへ追加し、監査ログに残す（アプリをチャンネルに追加するのと同じ扱い。ゲストは承認できない）
- Cairn AI は Cairn 本体の一部なので、投票アプリと違い Bot API の HTTP を通らず、同じ投稿関数（`chatPostMessage`）を直接呼ぶ。インタラクションの受け口と作成メニューの起動口は持たない
- `/ai` の承認カードは会話の中の画面部品として描く（チャンネルのメッセージではないため、カード型メッセージ＝ blocks にはしない）。投稿されるメッセージ側はカード型メッセージ（markdown + context）で描く
- 実行案を作る tool（`propose_*`）は用意済みで、`/ai` への接続は Skill の呼び出し（Phase 1 の次の PR）で行う。それまで `/ai` は読み取り専用のまま

### 11.3 Phase 1（定義の保存と設定画面）の実装で決めたこと（2026-10-28）

- `ai_automations` / `ai_automation_runs` は Phase 2 から前倒しして作る（Skill の定義と実行記録の置き場が要るため）。組み込みの PMO の行（`builtin`）は Phase 2 で入れ、設定画面の一覧には出さない
- この段階で作れるのは Skill だけ。API は cron / heartbeat を「現在作成できるのは Skill だけです」で断る
- Skill の名前は英小文字で始まり、半角英小文字・数字・ハイフンの40文字以内（`$名前` を本文から曖昧なく切り出し、`$100` のような金額と取り違えないため）。ワークスペース内で一意で、DB の一意制約でも強制する
- 書き込みの種類は、保存時に作成者がチェックボックスで選ぶ（指示文から LLM に推定させない）。選んだものだけを Skill の実行時に `propose_*` tool として渡し、どれも承認カードを通す。何も選ばなければ読み取り専用
- §2.6 の注意（評価・報告を含む指示文は公開される）は、指示文の中身を判定せず、作成・編集フォームに常に表示する
- 定義の上限（20件）は、作成時にワークスペース単位のアドバイザリロックの中で数えて、同時に作っても超えないようにする
- 削除しても実行記録は残す（`ai_automation_runs.automation_id` は set null、`workspace_id` を持つ）。監査のためと、1日の実行回数の上限を削除・作り直しで戻させないため。停止から再開すると `paused_reason` も消す
- 一覧（`GET /api/automations`）は member 以上。guest には見せない（§2.5）。作成・編集・停止・削除は admin 以上

### 11.4 Phase 1（Skill の呼び出しと dry-run）の実装で決めたこと（2026-10-28）

- `/ai` の依頼が `$名前` で始まるときだけスキルとして実行する（先頭以外の `$` や `$100` のような金額は対象外）。名前の後ろは、そのスキルへの追加の依頼として渡す。入力欄で `$` を打つと、停止中でないスキルを候補に出す
- スキルを呼べるのは member 以上（一覧をゲストに見せないため、呼び出しもそろえる）。見つからない・停止中のときは、課金の前にエラーで返す
- 指示文は system prompt の【スキル】に、ワークスペースの追加指示と同じく区切りタグで囲んで入れ、権限・安全規律より優先させない。書き込みの tool（`propose_*`）は、スキルで許可した種類だけを渡す（説明文で禁じるだけにせず、tool 自体を渡さない）
- tool calling の上限は、スキルでは12ステップ（通常の調査は8）。読む → 判断する → 実行案を作る、まで進めるため。1回の呼び出しに数分かかるため、`/ai` の送信とテスト実行の API は `maxDuration = 300`（Vercel Pro の既定。上限は 800 秒）にする
- 呼び出し1回ごとに run を1件残す（trigger_key はアシスタントの応答 ID）。読んだ根拠（evidence）と作った実行案の ID を記録する。1日の上限（100回）に達した呼び出しは `skipped` として記録して断る。上限到達時の作成者への通知は、cron（Phase 3）と一緒に入れる
- dry-run は設定画面の各スキルの「テスト実行」から、admin 以上が行う。停止中のスキルも試せる。実際に読んで判断するが、`propose_*` は実行案を保存せず、内容の検証（対象が見えるか）だけをして結果に集める。回答・提案される操作・読んだもの・失敗した tool を画面に出し、run にも `dry_run = true` で残す。クレジットと実行回数を消費する
- 役割を付ける実行案のために、役割の ID を返す `list_project_roles` を追加し、`get_project_members` と `get_member_history` も役割 ID を返す

### 11.5 `@役割` と指示文の入力補完の実装で決めたこと（2026-10-28）

- チャットの `@役割`（`<@role:役割ID>`）は、プロジェクトチャンネルとその配下でだけ候補に出し、そのプロジェクトでその役割を持つ active メンバーへ通知を展開する（属性と同じくアクセスフィルタを通す）。プロジェクトに紐づかないチャンネルでは誰にも展開しない。Expo アプリの入力欄にも役割の候補を出す（`apps/web/AGENTS.md` の「`/chats` の変更はネイティブにも」に従う。属性の候補は従来どおり Web だけ）
- 指示文の入力欄では `@` でメンバー・属性・役割、`#` でチャンネルを選び、`<@id|名前>`・`<#id|名前>` の形で入れる。保存時に名前を落として ID だけにし（`canonicalizeInstructionReferences`）、一覧の表示と実行時に、読む人の権限で名前を解決し直す。見えないチャンネルは「非公開のチャンネル」と表示する（一覧はメンバー全員が見るため）
- 実行時の指示文には ID と名前の両方を残し、system prompt で記法の意味を説明する。AI は名前で依頼を理解し、ID でそのまま tool を呼べる
- 入力欄は ID を含む記法のまま表示し、その下に `@名前`・`#名前` のプレビューを出す（チャットの入力欄のような名前への置き換えは、利用状況を見てから検討する）
