# AI常駐PMO設計書 — プライベートナッジによるプロジェクト推進支援

作成日: 2026-07-17
ステータス: 構想・設計段階（実装未着手）

AI時代の「プロジェクト推進ツール」の中核仮説 —— **AIが良いPMOのように常駐し、裏方としてプロジェクトを前に進める** —— を要求と設計に落としたもの。

[`docs/10_ai_member_design.md`](./10_ai_member_design.md) の Stage 3「心拍を持つ（半自動）」を具体化・先行実装する位置づけ。ただし Stage 3 が想定する「チャンネルでの公開発言」とは異なり、本設計は**本人だけに見えるプライベートナッジ**を配信の第一形態とする（理由は §1.2）。

---

## 1. コンセプト

### 1.1 「PMO常駐」とは

- AIが定期的にワークスペースを巡回（ハートビート）し、プロジェクトの停滞・リスクの兆候を検知する
- 検知したら、**関係する本人にだけ**チャット欄の文脈の中でそっと知らせる
- 例:「タスク『装備リスト確定』の期限が明後日ですが、まだ着手されていないようです」

### 1.2 プライベートナッジが第一形態である理由

この種の機能が失敗する最大の理由は、検知精度ではなく**リマインドが公開処刑になること**にある。遅れている人を全員の前で名指しすれば、ツールは「監視装置」として嫌われ、最悪の場合チャットに本音が書かれなくなる（検知の材料自体が消える）。

そこで:

- ナッジは宛先本人にのみ表示し、「**このメッセージはあなただけに見えています**」を常に明示する
- 良いPMOが廊下でそっと声をかけるのと同じ振る舞いを、プロダクトの原則として固定する
- チーム全体に関わるリスクの公開発言（Stage 3 本来のスコープ）は、プライベートナッジで信頼を獲得した後の後続フェーズとする

### 1.3 成否を分けるのは「言わない判断」

的外れな指摘を2〜3回されたユーザーはナッジをミュートし、機能は形骸化する。本設計では検知アルゴリズムと同等以上に、**誤指摘率と鬱陶しさの制御**（重複抑止・クールダウン・頻度上限・フィードバック学習）を一級の設計対象とする。

## 2. 要求

### 2.1 機能要求

| # | 要求 | 備考 |
|---|---|---|
| F-1 | 定期巡回（ハートビート）でワークスペースの状態を検査する | Inngest cron |
| F-2 | 「期限が近い / 過ぎているのに未着手」のタスクを検知し、担当者本人にナッジを送る | ルールベース（Phase 1） |
| F-3 | 「進行中のまま長期間更新がない」タスクを検知し、担当者本人にナッジを送る | ルールベース（Phase 1） |
| F-4 | チャットの流れから潜在リスク（結論が出ずに流れた議論・認識齟齬の兆候・未回答の依頼）を検知し、関係者本人にナッジを送る | LLM巡回（Phase 2） |

| F-6 | ナッジから対象（タスク・メッセージ）へ1タップで遷移できる | |
| F-7 | ナッジに対して「あとで」「これは問題ない」のフィードバックを返せる | 抑止学習の入力 |
| F-8 | 同一事象への指摘を繰り返さない（重複抑止・クールダウン） | dedupe キー |
| F-9 | ナッジ生成理由（どの検知器が何を根拠に発火したか）を記録する | デバッグ・信頼性検証用 |
| F-10 | 過去の経緯を添えた文脈付きナッジ（「この議論は2週間前に同じ結論が出ています」） | メッセージ埋め込み（Phase 3） |

### 2.2 非機能要求

| # | 要求 | 備考 |
|---|---|---|
| N-1 | **沈黙がデフォルト**。確信度が低い場合は発言しない | [`10_ai_member_design.md`](./10_ai_member_design.md) §5 の原則を継承 |
| N-2 | 頻度上限: 1ユーザーあたり1日 N 件まで（初期値 3） | 超過分は破棄（キューに溜めない。翌日には状況が変わっているため） |
| N-3 | AIの閲覧範囲は既存の権限モデルに完全準拠する | §7 参照 |
| N-4 | DM チャンネルは巡回対象外 | §7 参照 |
| N-5 | LLM コストは差分巡回 + gpt-4o-mini 一次判定で抑える | §5.2 参照 |
| N-6 | 静寂時間帯（深夜・早朝）にはナッジを配信しない | 生成はしてよいが配信を遅延 |

### 2.3 やらないこと（設計上の禁止事項）

- **公開の場での催促・名指し**。ナッジは本人以外に一切表示しない
- **管理者・リーダー向けの「遅れている人一覧」**。ナッジの存在・内容・既読状態を本人以外（owner / admin を含む）に見せる機能は作らない。集計・レポートも作らない。「炙り出しに使えない」ことがこの機能の信頼の根拠であり、要望があっても原則として拒否する
- **自動エスカレーション**。ナッジを無視し続けても、AIが勝手にリーダーへ報告することはしない（本人に「チームに共有しましょうか?」と提案するに留める）
- **DM の監視・巡回**
- **ナッジからの直接的な状態変更の自動実行**。タスク操作は本人の明示的なアクションを経る

## 3. 全体アーキテクチャ

```
Inngest cron（ハートビート）
  │
  ├─ Phase 1: ルール検知（SQL）
  │    tasks.dueDate × status × assigneeId → 候補
  │
  ├─ Phase 2: LLM 巡回（差分メッセージ）
  │    前回スキャン以降の新規メッセージがあるチャンネルのみ
  │    gpt-4o-mini 一次判定 → 発話候補のみ gpt-4o で精査
  │
  ▼
発話ゲート（言わない判断）
  重複抑止（dedupeKey）→ クールダウン → 頻度上限 → 静寂時間帯 → 確信度
  │
  ▼
ai_nudges 行を INSERT
  │  DB トリガー + realtime.broadcast_changes()（既存の Broadcast from Database 方式）
  ▼
本人のクライアントだけが invalidate → REST 再取得
  │
  ▼
チャット欄に「あなただけに見えています」カードを合成表示
  └─ フィードバック（あとで / 問題ない）→ 抑止学習へ還流
```

新しいインフラは不要。Inngest（導入済み）・Supabase Realtime（Broadcast from Database、導入済み）・pgvector（`document_chunks` 運用中）の組み合わせで成立する。

## 4. データモデル

### 4.1 `ai_nudges`（新規）

ナッジは**通常の `messages` 行にしない**。messages は Realtime でチャンネル全員に配信される前提であり、「本人だけに見える」を messages の上に実装すると配信・未読・既読の全経路に分岐が入るため。宛先ユーザーを持つ独立テーブルとし、チャットUI側でタイムラインに合成する。

```
ai_nudges
  id            uuid PK
  workspace_id  uuid NOT NULL → workspaces
  user_id       uuid NOT NULL → profiles        -- 宛先。本人のみ閲覧可（RLS / API 双方で強制）
  channel_id    uuid → channels                 -- チャット欄のどこに出すか（プロジェクトチャンネル）
  project_id    uuid → projects
  task_id       uuid → tasks                    -- 対象タスク（ルール検知時）
  message_id    uuid → messages                 -- 対象メッセージ（LLM検知時の根拠）
  detector      text NOT NULL                   -- 'task_due_soon' | 'task_overdue' | 'task_stalled' | 'llm_risk'
  dedupe_key    text NOT NULL                   -- 再発防止キー（§6.1）
  title         text NOT NULL
  body          text NOT NULL
  reason        jsonb NOT NULL DEFAULT '{}'     -- 発火根拠（検知器の入力スナップショット。F-9）
  status        text NOT NULL DEFAULT 'active'  -- 'active' | 'dismissed' | 'resolved' | 'suppressed'
  feedback      text                            -- 'later' | 'not_helpful' | null
  created_at    timestamptz NOT NULL DEFAULT now()
  responded_at  timestamptz

  UNIQUE (user_id, dedupe_key)
  INDEX (user_id, status, created_at)
  INDEX (channel_id, user_id)
```

- `status: 'resolved'` は対象の解消（タスク完了・期限変更）をハートビートが検知して立てる。ユーザー操作なしで消えるナッジは「AIがちゃんと見ている」体験になる
- `feedback: 'not_helpful'` は同一 `detector × 対象` の長期クールダウンに使う（§6.2）

### 4.2 `ai_scan_states`（新規・Phase 2）

LLM巡回の差分カーソル。チャンネルごとに「どこまで読んだか」を持ち、新規メッセージがあるチャンネルだけを巡回対象にする。

```
ai_scan_states
  channel_id            uuid PK → channels
  last_scanned_message_id  uuid → messages
  last_scanned_at       timestamptz NOT NULL

```

### 4.3 `document_chunks` の拡張（Phase 3）

`sourceType` に `'message'` を追加し、チャットメッセージを埋め込み対象にする。巡回には必須ではなく（§5.2）、ナッジへの文脈付与・過去経緯の検索（F-10）で効く。粒度は1メッセージ単位ではなく「同一チャンネル・近接時間帯のまとまり」でチャンク化する（短文が多くベクトルが痩せるため）。

## 5. 検知設計

### 5.1 Phase 1 — ルールベース検知（LLM不要）

`tasks` / `projects` の構造化データだけで高精度に判定できる領域。誤指摘がほぼゼロのため、**ここで「裏方PMO」の体験・配信基盤・発話ゲートを確立する**。

| detector | 条件（初期値） | 宛先 | dedupe_key |
|---|---|---|---|
| `task_due_soon` | `dueDate <= today + 3日` かつ `status = 'todo'` かつ `assigneeId IS NOT NULL` | 担当者 | `task_due_soon:{taskId}:{dueDate}` |
| `task_overdue` | `dueDate < today` かつ `status != 'done'` | 担当者 | `task_overdue:{taskId}:{dueDate}` |
| `task_stalled` | `status = 'in_progress'` かつ `updatedAt < now - 7日` | 担当者 | `task_stalled:{taskId}:{updatedAtの週}` |

- dedupe_key に `dueDate` を含めるため、期限が変更されたら（=状況が変わったら）再度ナッジできる
- ナッジの `channel_id` は対象タスクのプロジェクトチャンネル。ハートビートは 1日1回、各ワークスペースの朝（初期値 09:00 JST）に実行
- 閾値（3日・7日）は将来ワークスペース設定化する。初期はコード定数でよい

### 5.2 Phase 2 — LLM巡回（潜在リスク検知）

**チャットのベクトル化は巡回には使わない。** 巡回は「前回スキャン以降の新規メッセージ」を時系列のまま読ませる方が確実で、差分だけ読むためコストも抑えられる。

1. `ai_scan_states` を参照し、新規メッセージのあるチャンネル（DM除く）を列挙
2. チャンネルごとに直近ログ（新規分 + 文脈用の直前数十件）を **gpt-4o-mini** にPMOプロンプトで渡し、一次判定:
   - 結論が出ないまま流れた議論はないか
   - 未回答のままの依頼・質問はないか
   - 認識齟齬・スコープ膨張の兆候はないか
3. 候補が出たときだけ **gpt-4o** で精査し、確信度・宛先・文面を生成。確信度がしきい値未満なら破棄（沈黙がデフォルト）
4. 発話ゲート（§6）を通過したものだけ `ai_nudges` に INSERT

巡回頻度は6時間おき程度から開始し、コストと検知の鮮度を見て調整する。宛先の決定は「その事象に行動を起こせる本人」（依頼を受けた人・議論の当事者）に限定し、特定できない場合は発話しない。

### 5.3 Phase 3 — メッセージ埋め込みによる文脈付与

`document_chunks` に `sourceType: 'message'` を追加し、ナッジ生成時に関連する過去の議論をベクトル検索で引いて文面に添える。

- 例:「この論点は 6/28 の議論で『A案で進める』と一度決まっています」
- 既存の `/api/ai/conversations`（AIチャット）の検索コンテキストにもそのまま流用でき、投資が二重に効く

## 6. 発話ゲート（言わない判断）

ナッジ候補は以下を**すべて**通過した場合のみ配信する。

### 6.1 重複抑止

- `UNIQUE (user_id, dedupe_key)` により同一事象への再発火をDB層で防ぐ（`ON CONFLICT DO NOTHING`）
- `dismissed / resolved` 済みでも dedupe_key が同じ限り再送しない。状況が変わる（期限変更・新しい停滞週）と key が変わり、再送可能になる

### 6.2 クールダウンとフィードバック学習

- `feedback = 'later'`（あとで）: 同一対象への次のナッジを 2日 遅らせる
- `feedback = 'not_helpful'`（これは問題ない）: 同一 `detector × 対象` を 30日 抑止。同じ detector に not_helpful が続くユーザーには、その detector 自体の閾値を緩める（例: due_soon を3日前→1日前に）
- フィードバックは抑止にのみ使い、本人以外への表示・集計には使わない（§2.3）

### 6.3 頻度上限・静寂時間帯

- 1ユーザー1日 3件 まで。超過分は**破棄**する（翌日に持ち越さない。持ち越すと古い指摘が溜まって精度が落ちる）
- 静寂時間帯（初期値 22:00–08:00 JST）は配信しない。ハートビート実行時刻を朝に置くことで自然に回避しつつ、Phase 2 の高頻度巡回では配信遅延で対応する
- 優先順位はルール検知 > LLM検知（確実な指摘を優先枠に入れる）

## 7. 権限・プライバシー

- **AIの閲覧範囲は権限モデルに従う**。巡回はサービスロールで行うが、ナッジ生成時に「宛先ユーザーがその対象にアクセスできること」を `requireChannelAccess` / `requireProjectAccess` と同等の判定で必ず検証する。AI経由で見えないはずの情報が漏れる経路を作らない
- **DM は巡回しない**（N-4）。私的な会話をAIが読んでいるという感覚は、公開チャンネルの巡回とは受け入れられ方が質的に異なるため、初期スコープから除外する
- **非活性メンバーにはナッジを送らない**。宛先解決は `active_workspace_members` ビューを経由する（CLAUDE.md の認可規約に準拠）
- **ゲスト**は参加プロジェクトのタスク・チャンネルに関するナッジのみ受け取る
- `ai_nudges` の読み取りは `user_id = auth.uid()` 本人のみ（API層 + 将来のRLS双方で強制）。owner / admin にも例外を作らない

## 8. 配信・UI設計

### 8.1 チャット欄への合成表示

- ナッジは該当チャンネルのタイムライン上に、通常メッセージと視覚的に区別されたカードで表示する
  - AIエージェントのアイコン + 「このメッセージはあなただけに見えています」の常時表示
  - 本文 + 対象へのリンク（タスクを開く / 該当メッセージへジャンプ）
  - アクション: 「あとで」「これは問題ない」（+ タスク系は「完了にする」ショートカット）
- タイムライン上の位置は「配信時点の最新位置」。過去ログを遡ったときに埋もれないよう、チャンネル上部に未応答ナッジのピン表示も検討する（未決事項）
- チャンネルに紐づかないナッジ（例: プロジェクトチャンネルが無い場合）は通知ベルのみに出す

### 8.2 Realtime・通知との関係

- 配信は既存方式に従う: `ai_nudges` への INSERT に DB トリガーを張り、`realtime.broadcast_changes()` で**本人の user topic** に配信 → `RealtimeProvider` がナッジクエリを invalidate → REST 再取得。ポーリングは行わない
- アプリ内通知（ベル）には `notification_type = 'ai'`（enum 定義済み）で記録し、チャットを開いていなくても後から回収できるようにする
- **Push は初期は送らない**。ナッジは「開いたときにそっと目に入る」のが適切な強度であり、Push で割り込む価値がある確証を得てから解放する

## 9. 実装フェーズ

| Phase | 内容 | 完了条件 |
|---|---|---|
| 1 | `ai_nudges` テーブル + ルール検知3種 + ハートビート + チャット合成表示 + フィードバック | 期限3日前の未着手タスクの担当者に、本人だけに見えるナッジが届き、タスク完了で自動 resolve される |
| 2 | LLM巡回（`ai_scan_states` + 差分スキャン + 二段階判定）+ 発話ゲート完全版 | 1〜2週間の実運用で「役に立った」フィードバックが「問題ない（誤指摘）」を上回る |
| 3 | メッセージ埋め込み（`sourceType: 'message'`）+ 文脈付きナッジ | ナッジに過去の議論への参照が正しく付く |
| 4 | 公開発言への拡張（[`10_ai_member_design.md`](./10_ai_member_design.md) Stage 3 本体へ合流） | — |

Phase 1 を最初に置くのは、LLM を使わずに誤指摘ほぼゼロで「裏方PMO」の体験・配信基盤・発話ゲートを検証できるため。**検知の賢さより先に、介入の作法（頻度・口調・言わない判断）を安いやり方で確立する。**

## 10. 未決事項

- ナッジの文面トーン（AGENTS.md の人格定義とどう接続するか。Phase 1 は固定文面でよい）
- ワークスペース／ユーザー単位のナッジ設定（オフスイッチ・頻度・静寂時間帯のカスタマイズ）をどの段階で出すか。**個人単位のオフは Phase 1 から必須**とする想定
- タイムライン合成の位置仕様（未応答ナッジのピン表示・古いナッジの自動折りたたみ）
- `task_stalled` の「停滞」判定に チャットでの言及 を加味するか（Phase 2 のLLM判定と統合する案）
- プロジェクト全体のリスク（期限直前×未完了タスク多数）をリーダーに知らせるか。「本人以外に見せない」原則との整理が必要（リーダー自身が行動主体である、という整理は可能）
- モバイル（Expo ネイティブチャット）での合成表示の実装時期
