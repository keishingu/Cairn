# 外部チャットの取り込み（Teams 個人用コミュニティ）

**種別: 現行**（取り込み元は Teams 個人用だけ。§10 の旧設計から作り直した）

Microsoft Teams（個人用）のコミュニティ廃止に合わせて、エクスポート（チャット履歴・メディア）からグループの過去ログを Cairn のチャンネルに取り込む。エクスポートの形式と移行の可否は [`research/teams-community-export-analysis.md`](research/teams-community-export-analysis.md)（記録）を参照。

- **取り込みは移行支援として Cairn の運営側が行う**。利用者が自分で実行する機能にはしない（運営者は環境変数 `IMPORT_OPERATOR_USER_IDS` で指定する）
- **取り込んだ過去ログは、まず一時保管の表に置く**。発言者を確定してから `messages` に移す（公開する）
- **公開したメッセージは、送信者が最初から正しい普通のメッセージにする**。表示のたびに送信者を差し替える処理を、通常の読み取り経路に入れない

## 1. 全体の流れ

```
① 取り込み（運営者）
   Teams エクスポート → Parser（ブラウザ）→ 共通 Import モデル
   → 一時保管の表（import_staged_messages）と投稿者の表（import_identities）
   ※ この時点ではチャンネルに何も出ない

② 投稿者の確定
   Teams の投稿者ごとに、Cairn のメンバーに紐づける / Teams の名前のまま残す を決める
   紐づけは運営者に加えて、取り込み先ワークスペースの owner・admin もできる

③ 公開（運営者）
   会話ごとに、発言者が確定した投稿を messages に移す
   投稿者不明の投稿は「投稿者不明として一緒に公開する / 残す」を会話ごとに選ぶ

④ 後からの確定
   紐づけの追加・変更・解除（owner・admin）→ 公開済みの送信者を付け替える
   投稿者不明の投稿の発言者を外部データで補う（運営者）→ 残していた投稿を公開する、または送信者を付け替える
```

- 解析はブラウザで行う。フォルダ全体はサーバーへ送らない。読むのは `messages.json` と `media/` の画像だけで、`endpoints.json`（端末の鍵）・`invites.json`（招待リンク）は読まない
- Slack / Discord は Parser を足せば、②以降は同じ仕組みで扱える

## 2. 発言者の確定とは

| Teams 側の投稿者 | 状態 | 公開したときの送信者 |
|---|---|---|
| Cairn のメンバーに紐づけた人 | 確定 | その Cairn ユーザー本人 |
| 名前は分かるが紐づけていない人（エクスポートした本人の連絡先など） | 確定 | 投稿者ごとの取り込み用プロフィール（Teams の名前） |
| 名前は分からないが ID で区別できる人（リアクションにだけ出る参加者） | 確定 | 投稿者ごとの取り込み用プロフィール（「名前不明の参加者」） |
| 投稿者不明（ID も名前も無い投稿。検証データで約30%） | **未確定** | 会話の公開方法による（§4） |

- 投稿者不明の投稿は、エクスポートだけでは人ごとに区別できない（「匿名1」「匿名2」に分けられない）。発言者を確定するには、ブラウザのキャッシュ（IndexedDB）や他の参加者のエクスポートとメッセージ ID で照合する（§5）
- 表示名だけで自動では紐づけない。画面は表示名が一意に一致するメンバーを候補として出すだけで、人が選んだときだけ紐づける

## 3. 投稿者の持ち方（設計判断）

| 観点 | 旧: 共通の取り込みプロフィール＋表示の上書き | 新: 投稿者ごとの取り込み用プロフィール＋一時保管（採用） |
|---|---|---|
| 送信者 | 全員が1つの共通プロフィール。本当の投稿者は別の表 | 紐づけた本人、または投稿者ごとのプロフィール |
| 通常の読み取り経路への影響 | 送信者を表示するすべての経路（一覧・検索・ブックマーク・タスク詳細・`/ai` など8か所）で差し替えが要る。経路を足すたびに漏れる | 差し替えは不要。送信者の名前がそのまま正しい |
| 性能 | 取り込みを使わないワークスペースでも追加のクエリが走る経路がある | 追加のクエリは無い（除外は `messages` の1列の条件だけ） |
| 前例 | なし | アプリの Bot（インストールごとのプロフィール、ワークスペースのメンバーに入らない）と同じ |
| 紐づけ | 1列を設定するだけで、行は書き換えない | 公開済みメッセージの送信者を付け替える。一時保管の行に「どの投稿がどの投稿者か」が残るので、付け替えと解除を正確に行える |

**新しい形を採用する**。旧設計は一部のワークスペースのための機能で、通常の読み取り経路を広く変えていた。

- 取り込み用プロフィール: `profiles.kind = 'import'`、`auth.users` を持たず、どのワークスペースのメンバーにもならない（Bot と同じ扱い）。表示名は Teams の名前、または「名前不明の参加者」「投稿者不明」
- 表示名はデータとして持つ（表示言語で切り替えない）。Teams の名前と同じく、取り込み元のデータの一部として扱う
- ワークスペースごと・投稿者ごとに1つ作る（`import_identities.profile_id`）。投稿者不明はワークスペース・取り込み元ごとに1つ

## 4. 公開

- 公開は会話ごとに運営者が行う。会話ごとに、投稿者不明の投稿をどうするかを選ぶ
  - **投稿者不明として一緒に公開する**: 会話が欠けない。送信者は「投稿者不明」のプロフィール。後で発言者が分かったら付け替える
  - **残す**: 確定した投稿だけを公開する。会話は欠ける（約3割）。残した投稿は、後で発言者が分かった時点で公開する
- 公開するメッセージは、通常の投稿 API を使わず直接書き込む（Inngest の `message/created` を出さない。通知・AI の巡回・埋め込みは動かない）
  - `messages.id` は `UUID v5(ワークスペース, 取り込み元, 会話 ID, メッセージ ID)`。何度公開し直しても、別の参加者のエクスポートでも同じ ID になり二重にならない
  - `messages.created_at` は元の投稿日時、`updated_at` は編集日時
  - `messages.imported = true`（取り込んだ過去ログの印。§6）
  - 引用返信（`qtdMsgs`）は、同じチャンネルに公開済みの引用元だけ `parent_message_id` にする。スレッドは推定しない
- リアクションは `message_reactions` に入れる（送信者と同じく、紐づけた本人か投稿者ごとのプロフィール）
  - 投稿者不明の人のリアクションは1つのプロフィールにまとまり、同じ絵文字は1件になる（一意制約）。人数は結果レポートに残す
- 画像は通常のアップロード経路（署名付き URL → finalize）で、取り込み先チャンネルに保存する。同じチャンネルの中では同じ AMS オブジェクトを1回だけ保存し、別のチャンネルのファイルは使い回さない（`imported_files`）
- 完了時、取り込み先チャンネルの既読位置が無い人に既読位置を置く（Cairn での最初の投稿の直前。無ければ完了時刻）

## 5. 後からの確定

### 紐づけ（owner・admin、運営者）

- 対象は取り込み先ワークスペースの投稿者。紐づけ先はそのワークスペースのアクティブなメンバーだけ。投稿者不明は紐づけられない
- 紐づけると、その投稿者の公開済みメッセージとリアクションの送信者を、取り込み用プロフィールから本人に付け替える
  - 付け替える対象は一時保管の行（`published_message_id`）から決める。本人が Cairn で投稿したメッセージは変えない
  - 本人が同じメッセージに同じ絵文字を既に付けていたら、取り込みのリアクションの方を消す（一意制約）
- 紐づけの変更・解除は逆の付け替えを行う
- 1回の付け替えは1トランザクション。通知は出さない

### 投稿者不明の補完（運営者）

- ブラウザのキャッシュや他の参加者のエクスポートから、メッセージ ID ごとの投稿者を読み込み、一時保管の行の投稿者を差し替える
- 残していた投稿は公開する。投稿者不明として公開済みの投稿は、送信者を付け替える
- どのデータを正とするか（食い違ったときの扱い）は、実装時に決める（調査レポート §6.2）

## 6. 取り込んだ過去ログの印（`messages.imported`）

通常の処理への変更は、この印による除外だけにする。

| 箇所 | 扱い |
|---|---|
| 未読件数（チャンネル・プロジェクトのチャンネル・DM）、未読の初期位置 | 数えない。過去ログの日付が Cairn での投稿と重なっても未読にしない |
| AI の巡回（`lib/ai-nudges/llm-nudge-scan.ts`） | 対象にしない（巡回位置は進めない） |
| メッセージの編集・削除 API | 拒否する（過去ログは本人でも変えない） |
| メッセージの DTO | `imported: true` を返し、画面は「Teams から取り込み」の印を出し、編集・削除の操作を出さない |

送信者の表示（一覧・検索・ブックマーク・タスク詳細・`/ai`）は変えない。Expo のネイティブチャットも、編集・削除・ブロックの操作を同じく出さない。

- `messages.imported` は既定値 `false` の列なので、マイグレーションより先に動いた旧コードの INSERT は失敗しない。逆に新しいコードはこの列を読むため、マイグレーションの適用（`migrate.yml`）が Vercel のデプロイより遅れた短い間は、一覧・未読などが失敗しうる。マイグレーションは数十秒、ビルドは数分かかるので実際には先に終わる

## 7. データモデル

| 表 | 内容 |
|---|---|
| `import_jobs` | 取り込みジョブ（状態・件数・取り込めなかった情報のレポート。本文・氏名は持たない） |
| `import_job_conversations` | ジョブ内の会話ごとの取り込み先チャンネル・投稿者不明の扱い（`include_unknown` / `hold`）・進捗 |
| `import_identities` | Teams 側の投稿者。外部キー（`mri:` / `name:` / `anonymous`）・表示名・種類・取り込み用プロフィール（`profile_id`）・紐づけた Cairn ユーザー（`linked_user_id`、紐づけた人・日時） |
| `import_staged_messages` | 一時保管のメッセージ。会話 ID・メッセージ ID・投稿者・投稿日時・編集日時・本文・引用元・リアクション・画像の参照・属性・公開状態（`published_message_id`） |
| `imported_files` | AMS オブジェクトと Cairn のファイルの対応（取り込み先チャンネルごと） |
| `messages.imported` | 取り込んだ過去ログの印（`boolean not null default false`） |

- 一時保管の行は `(ワークスペース, 取り込み元, 会話 ID, メッセージ ID)` で一意。同じエクスポートを何度取り込んでも、別の参加者のエクスポートでも二重にならない
- 取り込みの表はすべて `.enableRLS()` で、`anon` / `authenticated` に権限を付けない
- 一時保管の行は公開後も残す（紐づけの付け替え・解除と、投稿者不明の補完に使う）。ワークスペースの削除で消える

## 8. 権限

| 操作 | できる人 |
|---|---|
| 取り込み（一時保管）・会話ごとの公開・投稿者不明の補完 | 運営者（`IMPORT_OPERATOR_USER_IDS`）で、取り込み先ワークスペースの owner・admin |
| 投稿者の紐づけ・変更・解除 | 取り込み先ワークスペースの owner・admin（運営者を含む）。設定の「Teams から取り込む」の「取り込んだ投稿者」から行う |

- 設定の「Teams から取り込む」は、運営者か、取り込んだ投稿者がいるワークスペースの owner・admin に出す（`GET /api/imports/access` の `allowed` / `canLink`。入口の出し分けだけで、判定の正は API）。運営者でない owner・admin には紐づけだけを出す
- 投稿者不明の補完は API（`POST /api/imports/unknown`）だけで、画面は無い
- 取り込み先は、そのワークスペースのアーカイブされていないワークスペースチャンネルで、非公開なら操作者が参加しているものだけ。1対1・会議チャットは取り込まない（画面で選べず、サーバーも会話 ID の種類で拒否する）
- 新しいチャンネルは非公開で作る。公開範囲と、元のメンバーへの周知の注意を画面に出し、公開前に確認を求める

## 9. 本文の安全性

- Parser は HTML を残さない（タグ・script・style・コメントを除去、`javascript:` などのリンクは文字列だけにする）
- 本文の Markdown 記号はエスケープし、`<@` の間に U+2060（WORD JOINER）を入れて、取り込み元の文字列が Cairn のメンションにならないようにする
- サーバーでも、自動リンク以外の `<` とメンション記法を含む本文を拒否する

## 10. 旧設計からの移行

旧設計（PR #782。develop に入っている。main には未反映、実データなし）から次のとおり変える。データが無いので、マイグレーションは破壊的に行う。

- 削除: `imported_messages`、`imported_message_reactions`、共通の「取り込まれた投稿」プロフィール（`00000000-0000-4000-8000-00000000c0de`）と `IMPORT_SENDER_PROFILE_ID`
- 追加: `import_staged_messages`、`messages.imported`、`import_identities.profile_id`、`import_job_conversations` の投稿者不明の扱い
- そのまま: `import_jobs`、`imported_files`、`profiles.kind` の `import`、運営者の判定（`IMPORT_OPERATOR_USER_IDS`）、Parser と共通モデル
- コードから外す: `lib/imports/display.ts` の表示の上書きと、それを呼ぶ8か所（メッセージ一覧・チャンネル内検索・横断検索・ブックマーク・タスク詳細・`/ai` の会話検索と読み取り）、代替名の翻訳（`fallback-names.ts`）
- 置き換える: 未読・未読の初期位置・AI 巡回の除外（送信者が取り込みプロフィールか → `messages.imported`）

develop → main のリリースは、この作り直しが入ってからにする（マイグレーション `20261107090000_stage_imported_messages.sql`）。

## 11. テスト

- Parser・HTML サニタイズ・日時・投稿者・リアクション・メディア（`packages/core/src/import/teams/*.test.ts`）。フィクスチャは架空の名前・ID だけの匿名データ
- 一時保管・公開（投稿者不明の扱いの2通り）・二重登録の防止・中断後の再開・画像の共有・紐づけの付け替えと解除・投稿者不明の補完・未読と AI 巡回の除外・編集削除の拒否・通知が出ないこと・ワークスペースの分離を、ローカルの Supabase に書き込む結合テストで確かめる（`IMPORT_INTEGRATION_DATABASE_URL` を指定したときだけ動く）
- 実データ（エクスポート）はリポジトリに入れない。検証はローカルで、件数だけを出力して行う
