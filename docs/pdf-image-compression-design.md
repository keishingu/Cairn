# PDF添付ファイルの画像圧縮 — 設計判断記録

- **ステータス**: 決定（実装はこれから。実装が進んだら別途「現行リファレンス」として仕様を書き起こす）
- **作成**: 2026-07-03
- **背景**: チャットに添付されたPDFの多くは、写真のスクリーンショットをPNGでそのまま貼り付けたものが大半で、ファイルサイズが不必要に大きい。PDF内の画像だけを検出して再圧縮し、テキスト・ベクター図形・レイアウトは変えずにファイルサイズを縮小したい。

このドキュメントは、実装方式を決めるまでの比較検討と、特に **依存ライブラリのライセンス判断（AGPL回避）** の考え方を残すためのもの。同種の「依存ライブラリを1つ足すかどうか」の判断が今後も出てくるため、判断軸として再利用できるようにしている。

## 前提となる制約

- 圧縮処理は Inngest ジョブとして実行する（`file/uploaded` イベント、`apps/web/src/lib/inngest/functions.ts`）。この Inngest ジョブは Next.js の API Route 経由で **Vercel のサーバーレス関数上** で実行される
- Vercel のサーバーレス環境には任意の OS バイナリ（apt でインストールするようなネイティブ実行ファイル）を同梱するのが困難。**Node.js プロセス内で完結する実装（純JS/WASM、または Vercel 対応済みのネイティブアドオン）が前提**になる

## 検討した選択肢

| 選択肢 | 実体 | Vercel serverless で動くか | ライセンス | 備考 |
|---|---|---|---|---|
| Ghostscript | ネイティブバイナリ | ❌ ほぼ不可 | AGPL / 商用（Artifex） | `gs -dPDFSETTINGS=/ebook` 等で画像を自動判定して再圧縮できる。定番だがバイナリ同梱が壁 |
| Stirling-PDF | Ghostscript等を内包する別サーバー（Docker） | ✅（別コンテナ経由でHTTPで叩く） | OSS（本体） | ソフト自体は無料だが、コンテナを別途ホストする運用コストが発生する |
| SaaS API（iLovePDF / Adobe PDF Services / CloudConvert 等） | 外部の従量課金API | ✅ | 各社商用 | 運用不要だが継続コストが発生。今回は不採用 |
| MuPDF単独（npm `mupdf`, WASM） | PDF専用エンジン。画像抽出〜再保存まで1ライブラリで完結 | ✅（WASM、バイナリ不要） | **AGPL / 商用（Artifex）** | 検討の結果、ライセンス上の理由で不採用（詳細は下記） |
| pdf-lib + sharp | pdf-lib（PDF構造操作）+ sharp（libvips、画像再圧縮） | ✅（両方Vercel対応） | **MIT（両方）** | **採用** |

## AGPLライセンスの検討（重要・再利用可能な論点）

Ghostscript も MuPDF も、開発元 Artifex が **AGPL-3.0 と商用ライセンスのデュアルライセンス**で配布している。無料で使う場合は AGPL の条件に従う必要がある。

### AGPLのネットワーク条項がいつ発動するか

AGPLは「**改変**して**ネットワークサービスとして提供**したとき」に、そのサービスの利用者へソースコード開示義務が生じる（無改変ならCairn本体は既にApache-2.0で全ソース公開しているため実害はない）。問題になるのは以下のケース：

- 第三者が Cairn をフォークし、独自の非公開カスタマイズを加えた状態でセルフホスト運用する場合、その改変版のソース開示義務が発生する

### 検討したメリット・デメリット

- **メリット（差別化になるのでは？という仮説）**: クローズドソースの競合SaaSがAGPL部品を組み込むには、商用ライセンス購入かソース公開のどちらかを迫られるため、タダ乗りされにくくなる（MongoDB SSPL、Elastic等の先例と同じ発想）
- **デメリット（セルフホスト導入への悪影響）**: 企業の法務・調達部門は、AGPLが実際に発動する条件を精査せず「**依存関係にAGPLが1つでもあれば社内利用禁止**」という一律ポリシーを持つことが多い。結果として「素のままセルフホストするだけなら実害ない」という理屈が通らず、**導入自体が却下されるリスク**がある

### 結論

差別化効果は限定的（競合には commercial license 購入や代替ライブラリという逃げ道が残る）一方、セルフホスト導入を妨げるリスクは具体的かつ非対称に大きいと判断し、**AGPL依存の追加は見送り**。MITライセンスの pdf-lib + sharp を採用する。

**今後の方針**: 依存ライブラリを追加する際、AGPL/SSPL等の強いコピーレフト系ライセンスは原則避け、MIT/Apache-2.0/BSD系を優先する（CLAUDE.mdにも追記）。

## 採用した設計

### エンジン

- **pdf-lib**: PDF構造の読み書き（画像XObjectの列挙・差し替え）
- **sharp**（libvips ベース）: 抽出した画像の実際の再圧縮（PNG→JPEG化）。Vercel対応のネイティブビルドが提供されている

### 差し替えやすさを優先したインターフェース設計

実験的な実装のため、圧縮エンジンを後から差し替えやすいよう、処理を1つの関数に閉じ込める：

```ts
// apps/web/src/lib/pdf/compress-images.ts
export async function compressPdfImages(buffer: Buffer): Promise<Buffer>
```

呼び出し側（Inngestジョブ）はこの関数の入出力にのみ依存する。中身を別エンジン（Stirling-PDF等）に差し替える場合も、この関数の実装を変えるだけで済む。ロールバックも「呼び出しをやめる」だけで完結する。

### 処理フロー

1. PR #284 で導入された3段階アップロードフロー（`upload-url` → 直接アップロード → `finalize`）により、PDFファイルは既に Supabase Storage 上にある
2. `finalize` は `isIndexable(mimeType)` が true の場合に `file/uploaded` イベントを発火する（`application/pdf` は該当）。既存のテキスト抽出インデックスジョブ（`indexFileChunks`）と同じイベントを、圧縮用の別 Inngest function が独立して購読する
3. 圧縮ジョブ: Storageから storagePath をダウンロード → `compressPdfImages(buffer)` → 同じ storagePath に上書き保存 → `files.fileSize` を圧縮後サイズに更新

### 圧縮対象の判定（写真スクショの狙い撃ち）

「写真のスクリーンショットをPNGで貼り付けている」という前提に合わせ、PDF内の画像XObjectのうち以下を満たすものだけを対象にする：

- `Subtype` が `Image`（`Form` XObject＝ネストした描画は対象外）
- `ImageMask` ではない
- 既に `DCTDecode`（JPEG）/`JPXDecode`（JPEG2000）で保存されているものは対象外（二重圧縮を避ける）
- 一定サイズ以上（アイコン・ロゴ等の小さい画像は対象外）
- 再圧縮後のバイト数が元より小さい場合のみ差し替える（圧縮で逆に大きくなるケースを避ける）

## 未決定・今後の検討事項

- 実装後、実際のPDFサンプルで圧縮率・画質を検証する
- 画像単体（PDFではなく `image/png` そのもののアップロード）の圧縮は今回のスコープ外。必要になれば別途 `file/uploaded` の対象を広げる
- 品質不足が判明した場合、`compressPdfImages` の中身を Stirling-PDF（別コンテナ）に差し替える選択肢を再検討する
