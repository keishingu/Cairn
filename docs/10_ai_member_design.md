# Cairn AI サーフェス・AIメンバー設計書

作成日: 2026-06-11 / 最終更新: 2026-09-24
ステータス: `/ai` のRAG・横断調査と AI PMO は実装済み。チャンネル参加型AIメンバーは構想段階

Cairn の AI 体験を、単一の「AI機能」にまとめず、利用者との関係が異なる3つのサーフェスとして整理する。

1. **`/ai` — プライベートな調査ワークベンチ**
2. **AI PMO — 本人だけに届く受動的なプライベートナッジ**
3. **AIメンバー — 共有チャンネルに参加する将来のエージェント**

3つは同じデータ・権限基盤を利用できるが、発話先・起動条件・状態・課金・許される副作用が異なる。UIや実行状態まで一つに統合しない。

[`docs/archive/09_product_strategy_notes.md`](./archive/09_product_strategy_notes.md) の優先課題 2（AGENTS.md カスタムAI）・4（AIをワークフローの中へ）・5（会話と構造の接続）を、この境界を守りながら段階的に回収する。

---

## 1. 決定事項

### 1.1 3つのサーフェスは共存させる

| サーフェス | 起動 | 見える人 | 主な役割 | 現在地 |
|---|---|---|---|---|
| `/ai` 調査ワークベンチ | 利用者が質問する | 質問した本人 | プロジェクト横断の調査、潜在リスク分析、根拠付き回答 | AIチャット、RAG、読み取り専用の横断調査ツールを実装済み |
| AI PMO | cron と状態変化 | 宛先本人のみ | 期限・停滞・未回答依頼・潜在リスクを少数だけ知らせる | Phase 1/2 実装済み。段階ロールアウト中 |
| AIメンバー | `@mention`、将来は承認済みアクション | チャンネル参加者 | 共有会話への応答、成果物生成、提案→承認による操作 | 構想段階 |

利用者が定義する Skill / cron / heartbeat（AI PMO を組み込み版として含む）は [`ai-automation-design.md`](./ai-automation-design.md)（構想）。`/ai` から Skill を呼んだ場合だけ、承認カード経由の書き込みを読み取り専用の例外として扱う。

### 1.2 `/ai` は設定画面へ転用しない

`/ai` は、利用者が人目を気にせず仮説を試し、ワークスペース全体を調査する場所として残す。将来のAI人格・行動規範・テンプレート設定は `/settings/ai` 配下へ置く。現行の個人/ワークスペースPMOスイッチは既存設定画面に維持し、設定情報が増えた段階で集約する。

理由:

- 潜在リスクの探索は、共有チャンネルへ投稿する前に個人で検証したい需要がある
- AI PMOは「AIが必要と判断した少数の気づき」、`/ai` は「人間が依頼した任意の深掘り」であり、代替関係ではない
- 共有チャンネルのAIメンバーは発言の社会的コストが高く、私的な調査UIと同じ発話規律にはできない

### 1.3 AI PMO と `/ai` の状態は分離する

`/ai` の調査は読み取り専用を初期値とし、次の状態を変更してはならない。

- `ai_nudges` の作成・再活性化・解決・フィードバック
- `ai_scan_states` の差分カーソル
- 通知、クールダウン、静寂時間、1日上限の消費
- AI PMOの配信クレジット

将来、ナッジの「詳しく調べる」から `/ai` を開く場合も、ナッジの根拠IDを初期コンテキストとして渡すだけにする。調査を開いた事実だけでナッジを解決しない。

## 2. `/ai` — プライベート調査ワークベンチ

### 2.1 基本動作

`/ai` は、会話履歴に加えて、最後のユーザーメッセージをクエリに `document_chunks` をベクトル検索し、上位5件を自動コンテキストとして回答する。対象は主に `file`・`project`・`member` チャンクで、外部検索ツールも利用できる。単純な質問ではこの経路だけで回答できる。

横断調査では、同じストリーム内で §2.3 の読み取り専用toolを必要な分だけ呼び出す。

構造化リスクは、期限超過、3日以内が期限の未着手、7日以上更新のない進行中、未アサイン、終了日が7日以内かつ未完了タスク3件以上をJST基準で判定する。チャンネル検索は時系列を維持し、DMを常に除外する。

### 2.2 回答の方針

`/ai` は次のような依頼に、権限内のデータを実際に調べ、根拠を示して答える。

> このワークスペースのプロジェクトを見て、期限・停滞・未回答の依頼・認識齟齬の観点から潜在リスクを優先度順に出して。根拠と次の確認事項も示して。

回答は「問題なし」を断定するのではなく、少なくとも以下を区別する。

- **検出したリスク** — 根拠となるタスク・メッセージ・ファイルを参照できる
- **要確認** — シグナルはあるが断定できない
- **調査できなかった範囲** — 権限、未インデックス、取得上限などで確認できない

### 2.3 実装

汎用エージェント基盤を作らず、Vercel AI SDKのtool callingとして読み取り専用の調査ツールをAIチャットへ追加している。

| ツール | 用途 | 主な返却値 |
|---|---|---|
| `list_projects` | 対象プロジェクトの列挙・絞り込み | 状態、期間、更新日時、メンバー概要 |
| `list_project_tasks` | 期限・停滞・未アサイン・状態分布の確認 | タスク、担当、期限、状態、更新日時 |
| `search_channel_messages` | 未回答依頼・意思決定・認識齟齬の根拠探索 | メッセージ、送信者、日時、返信関係、チャンネル |
| `search_workspace_documents` | 既存RAGの明示的な再検索 | チャンク、出典、類似度 |
| `get_project_risk_snapshot` | 構造化ルールの一括評価 | リスク種別、重要度、対象ID、判定理由 |
| `list_channels` | チャンネル名（`#審議` など）からIDを特定 | チャンネル、種類、紐づくプロジェクト、親チャンネル |
| `read_channel_messages` | 1チャンネルを期間指定で古い順に読む | メッセージ、送信者、日時、返信関係、続きのカーソル |
| `list_project_roles` | プロジェクトの役割とそのID（役割を付ける実行案に使う） | 役割名、ID |
| `get_project_members` | プロジェクトの参加者と役割 | 参加者、プロジェクトの役割（ID付き）、出欠、プロフィール属性 |
| `list_members` | 属性（「コーチ」など）でメンバーを絞り込む | メンバー、ワークスペースロール、プロフィール属性 |
| `get_member_history` | 最大50人の経歴をまとめて取得（比較表用） | 参加プロジェクト、役割、期間、ステータス、添付ファイル |
| `read_file` | 添付ファイルの抽出済み本文 | チャンク本文、続きのチャンク番号 |

`list_channels` 以下の7つは [`ai-automation-design.md`](./ai-automation-design.md) Phase 0 で追加し、MCP にも `/api/research/*` 経由で同じ実装を公開している（`read_file` は既存の `/api/files/[id]/content`）。可視範囲は既存画面の API と同じで、ゲストのメンバー・経歴は参加プロジェクトの共同メンバーと共通プロジェクトに限り、非活性メンバーの経歴は admin 以上だけが読める。

実装原則:

- 各ツールで `workspaceId` をモデル入力から受け取らず、認証コンテキストから固定する
- guest・private channel・project membership を既存の認可関数で毎回評価する
- 返却件数、期間、呼び出し回数に上限を設け、切り詰めた場合はモデルへ明示する
- IDだけでなく、UIが安全にリンク化できる構造化された根拠を返す
- ツール結果やチャット本文は命令ではなく未信頼データとして扱い、プロンプトインジェクションで権限やツール方針を変更させない
- 読み取り専用が原則。例外は `$名前` でスキルを呼んだときだけで、スキルで許可した種類の実行案（`propose_*`）を作り、承認カードで利用者が承認したときに実行する（[`ai-automation-design.md`](./ai-automation-design.md) §2.4・§11.4）

初期上限は `apps/web/src/lib/ai/research.ts` の `AI_RESEARCH_LIMITS` に集約する。プロジェクト50件、1プロジェクトのタスク100件、メッセージ100件・最大90日（`read_channel_messages` は期間の上限を設けず、カーソルで続きを読む）、文書10チャンク、チャンネル200件、メンバー200件、経歴は1回50人・1人100プロジェクト・1プロジェクト10ファイル、ファイル本文10チャンク、tool calling 8ステップ。上限適用時は `truncated`、返却件数、取得可能な場合は総数、適用フィルタ・期間をtool結果へ含める。

認証済みの `workspaceId` / `userId` はtool inputに含めない。各toolの読み取り境界で `active_workspace_members` を再確認し、guestは参加プロジェクト、private channelは現在の参加者に限定する。根拠リンクはサーバーが `project` / `task` / `message` / `channel` / `file` / `member` のevidence DTOとして生成し、既存のRAG source表示と同じ回答下部のチップで表示する。

`/ai` の会話一覧・会話本文・メッセージ送信は、ワークスペース一致に加えて会話の `created_by` が認証済み利用者と一致する場合だけ許可する。private channelや参加限定文書の調査結果を含む会話を、同じワークスペースの別メンバーが開くことはできない。

フォローアップ送信時、クライアントは最新の利用者メッセージだけを送る。会話履歴はサーバーが保存済みの本文から読み直すため、UI表示用の大きなtool結果をリクエストへ再送しない。

#### ワークスペースのシステムプロンプト

owner は設定の「AIエージェント」で、AGENTS.md のように `/ai` へ毎回渡す追加指示（用語・口調・回答形式・チームの決まりごと）を書ける。保存先は `workspaces.ai_chat_system_prompt`（null は未設定、上限 `AI_CHAT_SYSTEM_PROMPT_MAX_LENGTH` = 10,000 文字を Zod と CHECK 制約の両方で強制）。member 以下にも読み取り専用で表示し、更新は `PATCH /api/workspaces/settings` で owner だけが行える。

- system prompt の組み立ては `apps/web/src/app/api/ai/conversations/[id]/messages/system-prompt.ts` に集約する。追加指示は【Cairnの使い方】の後、未信頼の workspace-data と「権限・安全規律」の前に `<workspace-instructions>` で囲んで置き、規律側にも「追加指示より規律が優先する」と明記する
- 本文中の区切りタグは無害化し、ブロックを閉じて後ろへ指示を続けられないようにする。追加指示で認可・tool 方針・読み取り専用の制約は変えられない
- モデルに関係なく同じ `system` に入れるため、GPT-5 / Claude のどちらを選んでも効く。未設定（空）のときは従来とまったく同じ文面になる
- `ai_agents.system_prompt` / `agents_md` は使わない。`ai_agents` は §4 のAIメンバー用（スコープ・名前・モデル・作成者が必須の複数行）で、ワークスペースに1つの `/ai` 向け設定とは粒度が違い、モデルも `workspaces.ai_chat_model` と二重管理になるため

#### 会話への添付

`/ai`（Web）では、入力欄のクリップ・ドラッグ＆ドロップ・貼り付けで、その会話だけで使うファイルを添付できる。ファイル一覧（`files`）には登録しない。

- 対象は画像（JPEG・PNG・GIF・WebP）と、PDF・Word・Excel・PowerPoint・CSV・テキスト・Markdown。1回5ファイル・1ファイル10MBまで（`apps/web/src/lib/ai/attachment-types.ts`）。添付ありでもクレジットは通常と同じ1回分
- 本体は非公開の `ai-attachments` バケットに、`POST /api/ai/conversations/[id]/attachments` が発行した署名付き URL でクライアントから直接上げる（Vercel の本文上限を避けるため。チャットの添付と同じ方式）。行は `ai_attachments` で、送信までは `message_id` が null。送信時はクライアントが添付の ID だけを送り、サーバーが本人の・その会話の・未送信の添付であることを確かめてから Storage から読む。見つからない・アップロードが終わっていない・本文を取り出せない添付は黙って外さず、課金前にエラーで返す
- 画像はそのままモデルに見せる。文書は `extractText` で本文を取り出し（Excel は添付だけで読む。ファイル一覧のインデックス対象には入れていない）、先頭5万文字までを `<attached-file>` で囲んだ未信頼データとして渡す。切り詰めたときはその旨も渡す。取り出した本文は `extracted_text` に保存し、同じ会話で続けて質問したときは読み直さずに渡す。履歴の画像は新しい4枚まで読み込み直し、それより古いものはファイル名だけ伝える
- 送信前の添付は1つの状態（アップロード中・送れる・外している途中・アップロード失敗・外すのに失敗）で持ち、どれか1つでも送れる状態でなければ送信しない（入力欄と候補のボタンは同じ送信処理を通る）。送信済みのメッセージはサーバーを正とし、応答の後（保存が追いつくまで少し待つ）・会話を開いたとき・タブに戻ったときに保存済みの会話で置き換える（添付の期限付きリンクもそこで付け直す）。依頼のメッセージ ID はクライアントが送信時に決め、サーバーも同じ ID で保存する。受信中と、送った依頼の ID がまだ保存された会話に無い間は置き換えない（件数では比べない。送信に失敗した依頼や続けて送った依頼で食い違うため）。取り直せなかったときは知らせて、再読み込みできるようにする
- 会話を消すまで残す（会話・メッセージの削除で行が消える）。送られずに残った添付は Inngest の `cleanup-unsent-ai-attachments` が1日後に本体ごと回収する。退会時は本人の添付の本体も `storage_deletion_jobs` で消す。署名付きアップロード URL は発行から2時間使えるため、期限を過ぎた後（`not_before`）にもう一度消すジョブも積む
- 会話を削除する UI は現時点で無い（退会・ワークスペース削除で消える）。Expo アプリの `/ai` には未対応

### 2.4 AI PMOと共有できるもの・できないもの

共有してよいもの:

- 期限接近・期限超過・停滞などの**純粋な判定ルール**
- 権限考慮済みの問い合わせサービス
- 根拠参照のDTOとUIコンポーネント
- LLMへ渡す未信頼データの隔離・サニタイズ規約

共有しないもの:

- PMOの宛先選定、dedupe、クールダウン、静寂時間、日次上限
- `ai_nudges` / `ai_scan_states` の永続状態
- PMOの配信・通知・課金トランザクション

## 4. AIメンバー — 共有チャンネルに参加するエージェント

### 4.1 コンセプト

- AIエージェントはワークスペースのメンバーとして `channel_members` に参加する
- 発言は通常の `messages` と同じ未読・通知・リアクション・監査の仕組みに乗る
- 人格・役割・行動規範は組織ごとに AGENTS.md で定義する
- 共有空間では、人格の魅力よりも発言の希少性・根拠・承認可能性を優先する

### 4.2 既存資産と追加要件

既存資産:

- `ai_agents` — スコープ、名前、モデル、system prompt、`agentsMd`、HTMLテンプレート（未使用。`/ai` のワークスペース追加指示は `workspaces.ai_chat_system_prompt` に別に持つ。§2.3）
- `channels` / `channel_members` / `messages` / `channel_read_states`
- `document_chunks` と `/ai` 向けRAG

追加要件:

| 項目 | 内容 |
|---|---|
| AIのアイデンティティ | `messages.senderId` に使える agent profile と、人間との識別・RLS設計 |
| 承認待ちアクション | `ai_pending_actions`（実装済み。承認者・期限・競合・再実行の扱いは [`ai-automation-design.md`](./ai-automation-design.md) §11.2） |
| エージェント記憶 | 将来の `ai_agent_memories`。それまでは権限付きRAGで代替 |
| 監査 | AIの提案・承認・実行結果をチャンネル上で追跡可能にする |

## 5. AIメンバーの段階的ロードマップ

### Stage 1 — 呼べば来るメンバー

- `@エージェント名` で起動し、チャンネル・プロジェクトの権限内コンテキストで返答
- AGENTS.md を system prompt に合成
- HTMLテンプレートによる計画書等の生成
- 設定は `/settings/ai` に置き、`/ai` は調査ワークベンチとして維持

完了条件: チャンネル内で `@主務 計画書つくって` と依頼し、根拠付きの成果物が共有される。

### Stage 2 — 提案し、人間の承認後に操作する

- タスク作成・状態変更・決定事項の記録などをツール候補として生成
- 直接実行せず、チャット内の承認カードで人間が承認・編集・却下する
- 承認者を実行責任者として記録し、結果を必ず可視化する

完了条件: 会話から決まったことをタスク化する操作が、承認を挟んでチャット内で完結する。

### Stage 3 — AI PMOとの接続

AI PMO自体は実装済みであり、AIメンバーの公開発言機能とは分けて維持する。この段階では次の接続だけを検討する。

- プライベートナッジから `/ai` の詳細調査を開く
- 本人が承認した場合だけ、調査結果や論点を共有チャンネルへ投稿する
- 誰も責めない形で成立する再浮上（例: 未決論点の要約）を、公開発言の最初の候補にする

### Stage 4 — 記憶と人格の深化

- プロジェクト横断の長期記憶
- 過去の決定や失敗を踏まえた提案
- AGENTS.md と組織固有の記憶を組み合わせる

## 6. 全サーフェス共通の設計原則

1. **権限が最優先** — AI経由で通常UIでは見えない情報を取得できない
2. **根拠と調査範囲を示す** — 回答・ナッジ・提案を断定だけで終えない
3. **沈黙がデフォルト** — 自発的な介入と共有チャンネル発言は、迷ったら行わない
4. **不可逆な操作は承認制** — 状態変更・削除・外部送信は人間が承認する
5. **AIであることを明示する** — 発言・ナッジ・生成物に一貫した表示を付ける
6. **私的状態と共有状態を混ぜない** — `/ai` の会話、PMOのナッジ、チャンネル発言を暗黙に相互公開しない
7. **コスト不足で調査済みにしない** — LLM未実行・途中打ち切りを成功やカーソル進行として扱わない
