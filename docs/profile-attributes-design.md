# プロフィール属性機能 設計

> **ステータス**: 実装前の確定設計（作成: 2026-09-01）
>
> 実装後に本書とコードが乖離した場合は、コードと [`CLAUDE.md`](../CLAUDE.md) を正とする。

## 1. 目的

メンバーに「3年生」「経済学部」のようなプロフィール属性を複数設定し、チャットで名前と一緒に表示する。

プロフィール属性はプロジェクト上の役割やシステム権限ではない。人物に付く情報として、同じワークスペース内の複数プロジェクトをまたいで共通利用する。

表示例:

```text
ワークスペースチャット / DM
山田太郎 [3年生] [経済学部]

プロジェクトチャット
山田太郎 [サブリーダー] [3年生] [経済学部]
```

## 2. 用語と責務

| 概念 | カーディナリティ | 例 | スコープ | 権限への影響 |
| --- | --- | --- | --- | --- |
| ワークスペースロール | メンバーごとに1つ | owner / admin / member / guest | ワークスペース | あり |
| プロジェクトロール | メンバー × プロジェクトごとに1つ | leader / subleader / member | プロジェクト | なし |
| プロフィール属性 | メンバーごとに複数 | 3年生 / 経済学部 | ワークスペース内の全プロジェクト | なし |

以下を不変条件とする。

- プロフィール属性を認可判定に使用しない。
- ワークスペースロールをチャットに表示しない。
- プロジェクトロールは、そのプロジェクトに属するチャットでのみ表示する。
- プロフィール属性はプロジェクトに依存せず、ワークスペースチャット・DM・プロジェクトチャットで共通表示する。
- 属性は全アカウント共通の `profiles` ではなく、ワークスペース内のメンバーに紐付ける。あるワークスペースの管理者による変更を別ワークスペースへ波及させない。

## 3. データモデル

既存の `workspace_members` に JSON 配列を追加する。

```ts
profileAttributes: jsonb('profile_attributes')
  .$type<string[]>()
  .notNull()
  .default([])
```

DB上の例:

```json
["3年生", "経済学部"]
```

### 3.1 `workspace_members` に持たせる理由

- `workspace_members` には既にワークスペース固有の表示名・アバター・ステータスがある。
- 同じ人物でも、所属先ごとに学年やプロフィール表現が異なりうる。
- チャットメッセージ取得は既に `workspace_members` を結合しているため、属性取得の追加クエリが不要になる。
- 属性マスターテーブルと割当テーブルを新設せず、入力順を保った配列を1回で更新できる。

既存の以下の概念は流用しない。

- `tags`: プロジェクト分類用。人物情報と混在させない。
- `member_experiences`: スキル・経験用で、現状はユーザー全体スコープ。短い表示属性とは責務が異なる。

### 3.2 入力制約

- 1メンバーにつき最大5件
- 1件につき1〜20文字
- 保存前に前後の空白を除去
- 空文字列は禁止
- 空白除去後の完全一致を重複とみなし、重複は禁止
- 配列順を表示順として保持
- 色・アイコンは保存しない

Zodスキーマを `packages/shared` に置き、管理APIの入力を一箇所で検証する。DB migration は後方互換なカラム追加とし、既存行には空配列を設定する。

`active_workspace_members` は `workspace_members` を元にしたビューである。Drizzle側のビュー定義にも新カラムが現れるため、migration ではビューを再作成し、DB上の列定義とのずれを残さない。

## 4. 権限

| 操作 | owner | admin | member | guest |
| --- | --- | --- | --- | --- |
| 閲覧 | 可 | 可 | 可 | 既存のメンバー可視範囲内で可 |
| 属性の設定・削除 | 可 | 可 | 不可 | 不可 |

- 管理者は同一ワークスペースの active メンバーだけを編集できる。
- 非活性メンバーの属性は履歴表示のため保持するが、再活性化まで編集不可とする。
- owner の属性も admin が編集できる。属性は権限に影響しないため、ロール変更時の owner 保護ルールは適用しない。
- 本人による自己編集は初期スコープに含めない。必要になった時点で、管理者管理の属性と競合しない編集方針を別途決める。

## 5. API

### 5.1 管理API

属性配列全体を置き換える専用エンドポイントを追加する。

```http
PATCH /api/workspaces/members/:userId/profile-attributes
Content-Type: application/json

{
  "attributes": ["3年生", "経済学部"]
}
```

成功レスポンス:

```json
{
  "userId": "...",
  "profileAttributes": ["3年生", "経済学部"]
}
```

専用エンドポイントにする理由は、既存の `PATCH /api/workspaces/members/:userId` がロール変更と非活性化を扱っているためである。属性更新を同じ分岐へ混ぜず、認可と入力検証を独立させる。

更新後は編集したクライアントの以下のQueryをinvalidateする。

- `['workspace-members']`
- `['messages']`

### 5.2 メンバー取得

`WorkspaceMemberDto` に追加する。

```ts
profileAttributes: string[]
```

ゲストのメンバー可視範囲は既存仕様を変更しない。見えないメンバーの属性だけが新たに漏れないよう、既存のメンバー一覧・チャンネルアクセス境界の内側で返す。

### 5.3 チャットメッセージ取得

`MessageDto` に次を追加する。

```ts
senderProfileAttributes?: string[]
senderProjectRole?: ProjectMemberRole | null
```

- ワークスペースロールはチャットDTOへ追加しない。
- `senderProjectRole` はチャンネルに `project_id` がある場合だけ、そのプロジェクトの `project_members.role` から取得する。
- 別プロジェクトのロールを返さない。
- 新旧Web・Expoクライアントの混在に備え、新フィールドを受け取れない旧クライアントには影響しない追加レスポンスとし、新クライアント側は欠落時を空配列 / `null` として扱う。

メッセージ一覧では `channels` と `project_members` をまとめて結合する。`project_members` には `(project_id, user_id)` の一意制約があるため、メッセージ行は増殖しない。送信直後のレスポンスとクライアント生成IDによる冪等再送レスポンスにも同じ2フィールドを含める。

属性とロールはメッセージ投稿時のスナップショットとして保存しない。表示名と同様に、メッセージ取得時点の最新状態を表示する。

## 6. UI

### 6.1 表示ルール

| 表示場所 | ワークスペースロール | プロジェクトロール | プロフィール属性 |
| --- | --- | --- | --- |
| ワークスペースチャット | 非表示 | 非表示 | 表示 |
| DM | 非表示 | 非表示 | 表示 |
| プロジェクトチャット | 非表示 | 表示 | 表示 |
| メンバー詳細 | 既存どおり表示 | プロジェクト履歴内で表示 | 表示・管理 |
| メンバーカード | 既存どおり表示 | 非表示 | 表示 |

チャット内の順序は次とする。

```text
表示名 → プロジェクトロール → プロフィール属性 → 投稿日時
```

プロジェクトロールの既定値 `member` は、プロジェクト参加者であることと同義で情報量が少ないため表示しない。`leader` / `subleader` / `reviewer` / `observer` を表示する。

プロフィール属性は最大5件の制約があるため、チャットでは省略せずすべて表示する。PCは名前と同じメタ行で折り返し可能にし、モバイルは名前・プロジェクトロールの下へ属性行を折り返す。属性のために表示名や投稿時刻を省略しない。

### 6.2 見た目

- プロジェクトロールは既存のロール色を再利用する。
- プロフィール属性は `--card-2` / `--text-3` の中立色とし、権限や状態を示す色と区別する。
- 属性ごとの色指定は設けない。
- PC / Webモバイルでは共通の属性表示コンポーネントを利用する。
- Expoネイティブチャットは同じ情報設計で、React Native側の既存テーマ色を利用する。

### 6.3 管理導線

メンバー詳細パネルに「プロフィール属性」セクションを追加する。

- owner / admin にだけ「編集」を表示する。
- 編集時は既存属性をチップとして並べ、削除とテキスト入力による追加を行える。
- 複数項目をまとめて変更するフォームなので、「保存」「キャンセル」で確定する。
- 保存失敗は入力内容を保持したままインラインエラーを表示する。
- 非活性メンバーでは属性を表示するが編集操作を出さない。

初期スコープでは、属性マスターの設定画面、候補のオートコンプリート、ユーザー自身の設定画面は作らない。

## 7. Realtime・履歴・AI

### 7.1 Realtime

初期実装ではプロフィール属性専用のBroadcastトピックを追加しない。

- 編集した管理者の画面はmutation成功後のQuery invalidateで即時更新する。
- 他クライアントは次のREST再取得、画面再表示、メッセージ更新時に最新属性へ追従する。
- 属性変更を全参加者へ即時反映する要求が出た場合に、ワークスペース単位のprivate topicを設計する。

### 7.2 履歴

- 過去メッセージにも現在の属性を表示する。
- 属性の変更履歴・変更者監査ログは初期スコープ外とする。
- 非活性化しても属性は削除しない。再活性化時に同じ属性を復元する。
- アカウント削除時は既存どおり `workspace_members` と一緒に削除し、履歴上の表示名は匿名化された `profiles` にフォールバックする。

### 7.3 AI

プロフィール属性を既存のメンバーEmbeddingへ自動投入しない。学部や学年をAIの人物検索・推薦に利用するかは、UIでの表示とは別に利用目的と公開範囲を決める必要がある。

属性による人物検索を実装する場合は、公開範囲・本人訂正・AI回答での利用可否を決めてから `member/upserted` のインデックス対象へ追加する。

## 8. 実装対象

### Phase 1: 保存・管理

- `workspace_members.profile_attributes` とmigration
- `active_workspace_members` ビューの再作成
- Zod入力スキーマ
- 管理API
- `WorkspaceMemberDto` への追加
- メンバー詳細の表示・管理UI
- メンバーカードへの属性表示

### Phase 2: チャット表示

- Webのメッセージ取得・投稿DTO
- Webチャットの属性表示
- プロジェクトチャットでのプロジェクトロール取得・表示
- ExpoのメッセージDTOとネイティブチャット表示

DB変更は後方互換であり、Phase 1とPhase 2を同一リリースに含めなくても旧クライアントは動作する。ただしユーザーに見える完成条件は、Web・Expoのチャット表示まで含む。

## 9. 検証項目

### 自動テスト

- 5件・20文字・空白除去・重複拒否の入力検証
- owner / admin はactiveメンバーを更新できる
- member / guest は更新できない
- 別ワークスペースと非活性メンバーは更新できない
- ワークスペースチャットとDMは属性を返し、プロジェクトロールを返さない
- プロジェクトチャットはそのプロジェクトのロールと属性を返す
- 別プロジェクトのロールを返さない
- ワークスペースロールをチャット表示へ渡さない
- 既定のプロジェクトロール `member` を表示しない
- 属性のない既存メンバー・旧レスポンスでもチャットが壊れない

### 手動確認

- PCチャットで日本語5属性が折り返しても投稿時刻と本文が崩れない
- WebモバイルとExpoで、属性が名前の下へ折り返される
- プロジェクトを切り替えるとプロジェクトロールだけが切り替わり、属性は共通して残る
- 属性更新後、メンバー詳細・カード・チャットに最新値が表示される
- ダークテーマと各アクセント色で、属性が権限・ロールより控えめに見える

## 10. 初期スコープ外

- 属性マスター・カテゴリ・キーと値の構造化
- 属性ごとの色・アイコン
- 属性による検索・絞り込み
- 本人による自己編集
- 変更履歴・監査ログ
- 他クライアントへの即時Realtime同期
- AI検索・推薦への利用

これらが必要になった時点で、JSON配列から属性定義テーブル + メンバー割当テーブルへの移行を検討する。現時点では、最大5件の表示・一括編集には1カラムで十分である。
