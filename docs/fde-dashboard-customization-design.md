# FDE ダッシュボードカスタマイズ設計

作成日: 2026-09-23

ステータス: 設計（未実装）

## 1. 決定

Cairn のダッシュボードを、全顧客へ同じ情報を固定表示する画面ではなく、**FDE が顧客の業務上の関心を実装するカスタマイズ面**として設計する。

FDE は顧客ごとに「何が起きたら、誰が、何を見ると、次の行動へ進めるか」を定義する。Cairn は共通のデータアクセス、権限、Jev 判定、カード UI、監査、コスト制御を提供する。顧客固有の条件を製品コードの分岐や顧客専用フォークへ埋め込まない。

旧 `PageDashboard` の復元は目的にしない。新しいダッシュボードは、Jev がユーザーごとに表示価値を判定し、必要なカードだけを出す個人向けの運営画面とする。認証後の既定画面は当面 `/chats` のままとし、ダッシュボードの利用実績を見て変更を判断する。

## 2. プロダクト原則

1. **顧客の業務モデルを表現する**
   ステータス、プロジェクトロール、プロフィール属性、外部連携データを使い、顧客が実際に行う判断をカードへ変換する。
2. **沈黙を正常系にする**
   Jev が表示価値なしと判断した場合は何も載せない。カード数を埋めるための一般的な指標や AI 要約を生成しない。
3. **本人が行動できる情報を本人へ返す**
   管理者向けの監視画面ではなく、表示された本人が次の行動を取れるカードを優先する。
4. **顧客専用コードではなく設定へ閉じ込める**
   顧客差分は宣言的な設定にし、任意 SQL、任意 JavaScript、顧客別 React コンポーネントを許可しない。
5. **個別案件を共通基盤へ戻す**
   複数顧客で繰り返された候補抽出、カード、アクションは、業種別テンプレートまたは共通機能へ昇格させる。

## 3. 責務境界

| FDE が顧客ごとに定義するもの | Cairn の共通基盤が保証するもの |
|---|---|
| 顧客が重視する事象・例外・好機 | ワークスペース境界とアクセス制御 |
| 候補を抽出する条件 | 許可済みデータソースとクエリ実装 |
| 対象となる役割・人物・チーム | Jev の呼び出し、ZDR、利用量記録 |
| Jev に評価させる業務基準 | 表示しない選択、件数上限、重複排除 |
| カードの文言・優先順位・配置 | 標準カードコンポーネントとアクセシビリティ |
| 押した後の業務アクション | 許可済みアクション、監査ログ、失敗表示 |
| 必要な外部データ連携 | コネクタの認証情報管理とデータ隔離 |

FDE が新しい顧客へ提供する主成果物は、顧客専用画面そのものではなく、上表左側を表現した**ダッシュボードレシピ**である。

## 4. 処理の流れ

```text
Cairn の構造化データ・会話由来シグナル・外部連携
                         ↓
              決定論的な候補抽出
                         ↓
              顧客別ダッシュボードレシピ
                         ↓
       Jev が「現在有効か・表示価値・行動可能者」を判定
                         ↓
         ユーザー別に最大件数までカードをマテリアライズ
                         ↓
             共通カード UI と次のアクション
```

候補抽出は可能な限り決定論的に行う。Jev は大量の生データから自由生成するのではなく、候補の現在性、表示価値、対象者、優先順位を判定するために使う。

## 5. ダッシュボードレシピ

初期段階では、既存の `workspaces.settings` に Zod で検証する `dashboardSpec` を追加する方法を第一候補とする。以下は概念例であり、実装時の確定スキーマではない。

```ts
interface DashboardSpec {
  schemaVersion: 1
  enabled: boolean
  maxCards: number
  cards: Array<{
    id: string
    source: 'projects' | 'tasks' | 'messages' | 'integration'
    candidate: string
    audience: string
    evaluator: string
    cardType: string
    action: string
    title?: string
    priority: number
  }>
}
```

例:

```json
{
  "schemaVersion": 1,
  "enabled": true,
  "maxCards": 3,
  "cards": [
    {
      "id": "leader-missing",
      "source": "projects",
      "candidate": "leader_missing",
      "audience": "workspace_admin",
      "evaluator": "show_if_actionable",
      "cardType": "project_alert",
      "action": "open_project",
      "title": "責任者が未設定の案件",
      "priority": 100
    }
  ]
}
```

`candidate`、`evaluator`、`cardType`、`action` は自由記述コードではなく、Cairn 側の許可済みレジストリを参照する識別子とする。

## 6. Jev の役割

Jev は候補ごとに少なくとも以下を判定する。

- この事象は現在も有効か
- 今このユーザーに見せる価値があるか
- このユーザーが具体的に行動できるか
- 複数候補のうち何を優先すべきか
- 該当なしとして表示しないか

判定結果には根拠となるプロジェクト、タスク、メッセージ等の ID を保持し、カードから原文・対象画面へ遷移できるようにする。AI が生成した説明だけを根拠にしない。

ページ表示のたびに Jev を呼ばない。AI PMO の差分巡回と同様にバックグラウンドで評価し、ユーザー別の表示カードを保存する。再評価時には現在状態と照合し、解消済みカードを非表示にする。

ナッジより表示コストは低いが、ユーザーの注意を消費する点は同じである。最大件数、重複排除、鮮度、有効期限を共通基盤で制御する。

## 7. FDE 導入手順

1. **業務発見**
   顧客が毎朝確認する情報、見落とすと困る事象、実際に判断できる人、次の行動を聞き取る。
2. **候補とアクションの定義**
   「表示する情報」ではなく「誰が何をすれば仕事が進むか」を一組で定義する。
3. **レシピ作成**
   既存の候補抽出・評価・カード・アクションを組み合わせ、不足する共通部品だけを追加する。
4. **シャドー評価**
   実表示せずに候補、Jev の採否、対象者、根拠、費用を記録し、顧客と妥当性を確認する。
5. **限定公開**
   対象ユーザーと最大件数を絞って有効化し、カードから実際に行動へ進んだかを評価する。
6. **共通化判断**
   他顧客でも再利用できる部品はテンプレートまたは共通レジストリへ戻す。

案件の成功指標はダッシュボードの閲覧数ではなく、対象業務の見落とし減少、判断時間短縮、停滞解消など、顧客が達成したい成果で置く。

## 8. 安全境界

- すべての候補抽出は認証済みワークスペースと既存のアクセス制御を経由する。
- ゲストには参加プロジェクト外の候補・件数・存在を返さない。
- FDE 設定から任意 SQL、任意 URL、任意 JavaScript を実行しない。
- カードは採用理由、対象データ、評価時刻、有効期限を監査可能にする。
- 外部連携データはコネクタごとの権限と利用目的を明示する。
- プロフィール属性を Jev 判定へ利用する場合は、表示用途とは別に公開範囲・本人訂正・AI 利用可否を決める。
- 管理者向けの個人ランキング、遅延者一覧、自動エスカレーションは、既存の AI PMO 方針どおり作らない。

## 9. 段階導入

### Phase 1 — FDE 管理の宣言的設定

- `dashboardSpec` をワークスペース単位で保持する。
- 設定は FDE 向けの内部手段で投入し、顧客向けビルダーは作らない。
- 標準カードを少数用意し、表示は最大3件から始める。
- ダッシュボードは読み取り中心とし、アクションは既存画面への遷移に限定する。
- `/chats` を認証後の既定画面として維持する。

### Phase 2 — テンプレート化と外部連携

- 複数案件で再利用されたレシピを業種別テンプレートへ昇格する。
- 許可済みコネクタとカードアクションを追加する。
- レシピのバージョン、公開、ロールバック、適用履歴を管理する。

### Phase 3 — 顧客管理者による編集

- FDE が繰り返し設定する項目だけを管理画面へ公開する。
- 自由な BI ビルダーにはせず、テンプレート選択、文言、対象、順序、ON/OFF に限定する。

## 10. 実装開始条件

実装前に、最初の顧客案件について以下を確定する。

- 顧客が現在使っている確認表・会議・レポート
- 最初に置き換える判断を1〜3件
- カードを見る本人と、その人が取れる具体的な行動
- 必要なデータが Cairn 内にあるか、外部連携が必要か
- 誤表示と見落としのどちらを重く扱うか
- シャドー評価期間と、顧客成果を測る指標

この情報がない段階では、汎用ダッシュボードビルダーや多数のカードを先に実装しない。
