# Cairn UI統一ルール

2026-08-31の[UI統一作業（PR #531）](https://github.com/keishingu/Cairn/pull/531)で採用した、プロダクト画面の基準。
`interface-design` が今後の設計・実装時に読む保存先とし、品質確認にはVercel公式の `web-design-guidelines` を使う。
Skill本体は変更せず、Cairn固有の判断だけをここに保存する。LP・マーケティングページは対象外。

## 方針と適用範囲

- 山行・プロジェクト・タスクを確認し、その場で操作できる既存の情報密度を維持する。装飾やテーマ刷新より、同じ操作を同じ場所・見た目・挙動で使えることを優先する。
- 「統一」は同じ役割・同じデバイス内で行う。ツールバーと入力フォーム、PCとモバイルを一律の寸法にしない。
- 既存の共通コンポーネントとCSS変数を先に探す。見た目だけをコピーした別フォーム・別ダイアログ・別アイコンを増やさない。
- 以下の数値は今回の基準であり、普遍的なデザイン正解ではない。操作性・アクセシビリティ・新しい要件と衝突する場合は理由と影響範囲を示し、合意した変更後にこの文書も更新する。
- 読み取り専用のレビュー依頼は指摘までに留める。この文書はアプリ編集・commit・push・PR更新の許可を与えない。

## 見た目の基準

- 色は `globals.css` の `--bg` / `--card` / `--card-2` / `--text` 系、`--border` / `--divider`、`--accent` 系、意味を持つ状態色を使う。テーマ・アクセント設定を尊重し、画面ごとの色指定を増やさない。
- 平面の区切りは既存の細い境界線、重なるダイアログ・メニューは既存の `--shadow-*` で表現する。
- フォントは既存のInter / Noto Sans JP系を継承する。操作テキストは13px、フォームラベルは12px・600、モーダル見出しは15px・700を基準に、重みと文字色で階層をつける。
- レイアウトの余白は4px単位（8 / 12 / 16 / 20 / 24px）を基本にする。ラベル下・ボタン内の6pxなど、既存部品内の値はその部品を再利用して維持する。

## 部品と寸法

| 用途 | 再利用する実装 | 基準 |
| --- | --- | --- |
| 標準操作ボタン | `.btn`、主要操作は `.btn-primary` | 高さ34px、左右12px、角丸8px、アイコン間6px、13px・500（主要操作600） |
| コンパクトな入力 | `.form-control` | 高さ34px、左右10px、角丸8px |
| タスク作成・編集の入力 | `TaskFormFields`、`fieldInputStyle(false)` + `.form-control` | 高さ36px、左右12px、角丸8px。34pxのツールバーとは用途を分ける |
| PCのページ操作列 | `PageToolbar` | 上下12px・左右24px、操作列の最小高さ34px、左右ゾーン間12px、右側操作間8px |
| 分割選択ボタン | `SegmentedControl` | 全体34px、外側角丸8px・内側6px、内側余白2px |
| モーダル見出し | `ModalHeader` | 上下16px・左右20px、閉じる操作は右端 |
| タスクダイアログ | `TaskDialog` | 最大幅480px、角丸14px、本文余白20px・項目間16px、フッター余白16px 20px 20px |
| モバイルの主要作成入口 | 既存の `Fab` | 52px角、右16px、下ナビとsafe areaを避ける既存配置 |

PCの一覧・カレンダー・カンバンでは主要作成ボタンの高さ・上端・右余白を揃える。
親に `padding: 12px 24px 20px` があるカレンダー・カンバンは `PageToolbar inset` と下余白20pxを使い、余白を二重にしない。
同じ画面内のタブ・フィルター・ビュー切替も操作列に揃える。本文やモーダルの余白まで24pxに置換しない。

## 作成・編集の導線

- PCの主要作成入口はツールバー右端の `plus` + `新規{対象名}`。対象名は既存の表示名設定（例: `projectLabel`）を使う。
- プロジェクト作成はPCの `CreateProjectModal`、モバイルの `CreateProjectSheet` を再利用する。カンバンも作成入口を欠かさない。日付を選んで作成するカレンダーなど、文脈に必要な入口と初期値は維持する。
- タスク作成・編集は `TaskDialog` + `TaskFormFields` を使う。プロジェクト詳細だけ独自の作成モーダルを再実装しない。対象プロジェクト・チャンネル・担当者などの文脈と権限制御は保つ。
- ダイアログの見出し・閉じる操作・スクロールする本文・下部のキャンセル／確定操作は共通部品に任せる。確定は右側の主要ボタンにする。
- クリック・キーボードショートカット・FABの全入口で同じ作成権限を確認する。既存の `useWorkspacePermissions()` とサーバー側の認可を維持する。
- 作成成功時の閉じる・一覧更新・詳細表示は既存フローに合わせる。特に `CreateProjectSheet` は自身でキャッシュに追加するため、呼び出し側で同じ項目を再追加しない。

## アイコンと操作の意味

| 意味 | 共通 `Icon` の名前 | 区別すること |
| --- | --- | --- |
| 作成・追加 | `plus` | 入口には対象が分かるラベルを付ける |
| 閉じる・解除 | `close` | アーカイブやデータ削除の代用にしない |
| アーカイブ | `archive` | 箱の形を使い、閉じる×と混同させない |
| 削除 | `trash` | 削除対象をラベル・確認文で明示する |
| 行の追加操作 | `more` / `RowActionMenu` | 編集・削除をホバー時だけ現れる小アイコンに分散させない |

`Icon` の線幅・形状を共有する（標準線幅1.7、標準サイズ18px）。ボタン内13px、モーダルの閉じる16pxなど、同じ用途同士でサイズを揃える。
アイコンだけのボタンには `aria-label` を付ける。
保存済みフィルター削除は `ConfirmDialog` で確認し、対象がフィルターであってファイルではないことを示す。キャンセル時は更新せず、失敗時はエラーと再試行できる状態を残す。

## 操作性と検証

- 操作はネイティブの `button` と `onClick` を使い、マウス押下だけに依存しない。`RowActionMenu` のEnter／Spaceによる開閉、Escapeで閉じてトリガーへフォーカスを戻す挙動を維持する。
- 入力の `label` と `id` を関連付け、複数フォームのID衝突を避ける。`.form-control:focus-visible` のアクセント色2pxアウトラインをインラインの `outline: none` で消さない。
- 無効・送信中・空・エラーの状態を確認する。サイズ表だけでタッチ操作やアクセシビリティを満たしたと判断しない。
- PC／モバイルの切替は既存のUA判定に従う。幅を狭めるだけではモバイル分岐の検証にならない。Expoの共通ヘッダーはネイティブ側が所有し、WebViewに重複描画しない。
- 変更対象と同じ部品を使う画面を確認し、必要な型チェック・関連テストに加えて実画面で高さ・余白・はみ出し・フォーカスを確認する。モバイル実機を未確認ならその制約を明示する。
- 最終確認では `web-design-guidelines` が指定する最新のVercel公式ガイドラインを取得して照合する。ここにある寸法やルールだけで品質確認を済ませない。
- PR #531時点ではモバイル実機・ネイティブ操作と、実データ更新を伴うE2Eは未検証。共通モーダルの完全なフォーカストラップも今回の対応範囲には含まない。

## 実装の参照先

すべてリポジトリルートからの相対パス。

- `apps/web/src/app/globals.css` — 色・ボタン・入力の共通スタイル。
- `apps/web/src/components/app/primitives.tsx` — `Icon` / `ModalHeader` / `fieldInputStyle` / `Fab`。
- `apps/web/src/components/app/pages/page-toolbar.tsx` — `PageToolbar` / `SegmentedControl`。
- `apps/web/src/components/app/task-dialog.tsx`、`task-form-fields.tsx` — タスクフォームの共通構造（後者も同じディレクトリ）。
- `apps/web/src/components/app/row-action-menu.tsx`、`confirm-dialog.tsx` — 行操作と確認（後者も同じディレクトリ）。

現行の部品API・権限・プラットフォーム仕様はコードと `CLAUDE.md` を確認する。文書と実装に差があれば、意図的変更か不整合かを確認してから修正する。
